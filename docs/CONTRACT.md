# Формат проектов SeMaps — контракт v3

Нормативное описание того, **что считается корректным файлом модели на диске**.

Принят [`ADR_20260831_diagrams_text-provenance-and-view-axes`](adr/ADR_20260831_diagrams_text-provenance-and-view-axes.md),
развивает [`ADR_20260828_diagrams_model-contract-v2`](adr/ADR_20260828_diagrams_model-contract-v2.md).

## Кто про что рассказывает

Чтобы документы не разъезжались, у каждого одна тема. Дублировать содержимое
соседа не нужно — нужно ссылаться.

| Документ | Отвечает на вопрос |
|---|---|
| **этот файл** | что валидно на диске: поля, типы, инварианты |
| [`API.md`](API.md) | что обязан отдавать и принимать хост (сервер, WebView, CLI) |
| [`EXTRACTOR.md`](EXTRACTOR.md) | какие факты о коде поставляет извлекатель |
| ADR | почему именно так, и чем платили |

## 1. Структура проекта на диске

```
<workspace>/projects/<project_id>/
  project.json          манифест
  entities.json         каталог сущностей
  relations.json        каталог связей
  relation-types.json   словарь типов связей
  containers.json       контейнеры (принадлежность, не геометрия)
  text.<lang>.json      тексты с происхождением по полям
  views/
    <view_id>.view.json вид: ось, геометрия, размещения
```

Стили общие для всех проектов: `<workspace>/styles.json`, а если его нет — умолчание инструмента
[`host/defaults/styles.json`](../host/defaults/styles.json). То же для `templates.json` и `content/`.
Рядом с ним — ещё два общих реестра, оба введены
[`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md):
`templates.json` (шаблоны содержимого
блока) и `content/index.json`
(картинки для директивы `@Asset`, файлы `content/*.svg` лежат рядом). Оба формата — §11.

**Перечня видов нет** ([`ADR_20260923-7`](adr/ADR_20260923-7_contract_projects-and-views-found-not-listed.md)).
Проект — любая папка `projects/<id>/`, в которой есть `project.json`; вид — любой файл
`views/*.view.json` в ней. Каталог в редакторе двухуровневый: проекты, в них виды. Пустой
workspace (нет даже `projects/`) законен. Файл `catalog.json` упразднён: он не читается, а
`semaps check` сообщает о нём как об устаревшем.

**Базового языка нет.** Каталоги текстов равноправны; направление перевода
записано на каждом значении отдельно (§7).

## 2. `project.json`

```json
{
  "id": "core",
  "title": "Core Layer (src/core)",
  "subtitle": "Domain, MCP, Security, Host",
  "contractVersion": 3,
  "defaultView": "v_semantic_atlas",
  "defaultAxis": "axis_subsystem",
  "languages": ["ru"],
  "icon": "🧠",
  "sources": { "include": ["src/core"] },
  "styles": "../../styles.json"
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | совпадает с именем каталога |
| `title` | да | заголовок проекта; не переводится. Нет — в каталоге показывается `id` |
| `subtitle` | нет | вторая строка в каталоге |
| `contractVersion` | да | `3` |
| `defaultAxis` | нет | ось для видов, не объявивших свою (§8) |
| `languages` | нет | какие `text.<lang>.json` грузить; первый — основной для показа |
| `icon`, `theme`, `order` | нет | строка проекта в каталоге: значок, цветовая тема значка, место (по `order`, затем по `id`) |
| `sources.include` | нет | пути от корня репозитория для будущей сверки с кодом |

`id` проекта можно сменить: папка переименовывается, `project` в каждом виде переписывается
([`ADR_20260923-8`](adr/ADR_20260923-8_contract_project-and-view-ids-can-change.md)).

Поля `views` в контракте больше нет: виды — это файлы в `views/` (§1). Встретив его, считать
мусором.

Поля `baseLanguage` в v3 **нет**. Встретив его, считать мусором: направление
перевода задаётся не здесь.

## 3. `entities.json`

```json
{
  "entities": [
    {
      "id": "e_repetitionguardmiddleware",
      "name": "RepetitionGuardMiddleware",
      "kind": "class",
      "origin": "code",
      "status": "present",
      "namespace": "Acme.Agent.Guards",
      "codeRef": "src/Acme.Agent/Guards/RepetitionGuardMiddleware.cs",
      "symbol": "Acme.Agent.Guards.RepetitionGuardMiddleware",
      "members": []
    }
  ]
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | префикс `e_`. Выдаётся **один раз и не меняется никогда**, включая переименование типа |
| `name` | да | каноническое имя типа. **Не переводится**, в текстах его нет |
| `kind` | да | открытая строка: `class`, `interface`, `record`, `struct`, `enum` из кода; `external`, `app`, `assembly`, `database` — руками |
| `origin` | нет | `code` \| `authored`. v2-шное `manual` переименовано в `authored` |
| `status` | нет | `present` \| `missing` \| `planned`. Записи не удаляются: ушедшая сущность сохраняет `id` для ссылок |
| `namespace` | нет | пространство имён / пакет из кода |
| `codeRef` | нет | путь от корня репозитория |
| `symbol` | нет | `id` символа в фактах извлекателя ([`EXTRACTOR.md`](EXTRACTOR.md) §2.1, форма — [`ADR_20260923-5`](adr/ADR_20260923-5_extractors_symbol-ids.md)). Ключ, по которому `semaps sync` узнаёт сущность на следующем прогоне; ставит его сверка. Человек правит его в одном случае — подтверждая переименование в коде (EXTRACTOR §5). У `authored` не бывает. [`ADR_20260923-9`](adr/ADR_20260923-9_core_sync-symbol-mapping-and-containment.md) |
| `members` | нет | члены типа, для директивы `@Members` шаблона содержимого (§11.2) |

**Инвариант:** `id` уникален в проекте. Переименование типа — правка `name` при
неизменном `id`; ни один другой файл при этом не меняется. `symbol` уникален среди
не-`authored` записей: два одинаковых — реестр противоречит себе, `sync` не пишет ничего.

Сущность от символа `module` (сборка, пространство имён, файл) — обычная сущность:
`kind` — `nativeKind` символа (`assembly`, `namespace`, `file`).

**Форма `members`** ([`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md)
§2.4): массив объектов, каждый — один член типа.

```json
"members": [
  { "kind": "field", "name": "Retries", "type": "int", "visibility": "private" },
  { "kind": "method", "name": "InvokeAsync",
    "type": "Task<LlmTurnResult>", "visibility": "public",
    "note": "точка входа middleware" }
]
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `kind` | нет | открытая строка: `field`, `property`, `method` — то, что фильтрует `where=kind:…` в шаблоне; без него член просто не попадёт под такой фильтр |
| `name` | да | имя члена |
| `type` | нет | тип поля/свойства или сигнатура возврата метода |
| `visibility` | нет | `public` \| `private` \| … — открытая строка, используется и фильтром, и значком (замок у `private` задаётся в стиле, не в данных) |
| `note` | нет | короткая пометка, не переводится |

Разница между полем класса и колонкой БД — это значение `type`, а не отдельная
форма записи: `@Members` в шаблоне общий для обоих случаев (ADR §2.4).

**Совместимость.** Загрузчик по-прежнему принимает строку вместо объекта в
элементе `members` — она проходит насквозь как безымянный текст без `kind`, и
поэтому не проходит ни один `where=kind:…`. Новые записи следует заводить
только объектами.

## 4. `relations.json`

```json
{
  "contractVersion": 3,
  "relations": [
    { "id": "r_repguard_illmmiddleware_implements",
      "from": "e_repetitionguardmiddleware", "to": "e_illmmiddleware",
      "type": "implements", "origin": "code", "status": "present",
      "evidence": [{ "codeRef": "src/Acme.Agent/Guards/RepetitionGuardMiddleware.cs" }] }
  ]
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | префикс `r_`. Порождённая связь: `r_<from>_<to>_<type>` без префиксов `e_` |
| `from`, `to` | да | `id` сущностей |
| `type` | да | `id` из `relation-types.json` |
| `origin` | нет | `code` \| `authored` |
| `status` | нет | `present` \| `missing` |
| `evidence` | нет | `[{ codeRef, symbol?, line? }]` — проверяемое основание связи |

Порождённые сверкой типы: `extends`, `implements`, `contains` (вложенность: сборка /
пространство имён / файл содержит тип, тип — вложенный тип). `references` сверка не
пишет ([`EXTRACTOR.md`](EXTRACTOR.md) §5).

**`label` в v3 удалён.** Весь текст связи живёт в `text.<lang>.json` под её `id`;
фолбэка на структуру нет. Связь без текстовой записи рисуется без подписи — это
видно, и так и задумано.

**Подписи на концах** (`fromLabel`, `toLabel` — кардинальность, роль: «1»,
«0..*», «owner») живут там же, под тем же `id`, наравне с `name` (см. §7.2).
**У связи с `origin: "code"` текста нет вовсе** — ни `name`, ни `fromLabel`,
ни `toLabel`: `sync` перепишет его при каждом прогоне, а смысл несёт `type`
(см. §7.4, «фолбэка нет»).

## 5. `relation-types.json`

```json
{
  "contractVersion": 3,
  "relationTypes": [
    { "id": "implements", "origin": "code" },
    { "id": "call",       "origin": "authored" },
    { "id": "security",   "origin": "authored", "styleId": "edge.security" }
  ]
}
```

Тип связи — объект первого класса, а не свободная строка в `relations.json`.
Имя и описание — в текстах по ключу **`rt_<id>`**.

Множество типов **открыто**: проверки «такого типа не бывает» нет. Но тип,
которого нет в словаре, не имеет ни имени, ни описания, и потому бесполезен.

Отдельный файл, а не запись в `entities.json`: тот каталог частично порождается
из кода, и авторские строки утонули бы в шуме регенерации.

## 6. `containers.json`

```json
{
  "contractVersion": 3,
  "containers": [
    { "id": "c_llm", "parent": null, "theme": "green" },
    { "id": "c_llm_middleware", "parent": "c_llm",
      "match": { "name": ["ILlmMiddleware"], "path": ["src/Acme.Domain/Llm/Middleware/"] } }
  ],
  "overrides": { "e_repetitionguardmiddleware": "c_llm_middleware" }
}
```

- `id` — префикс `c_`; имя контейнера в текстах под тем же ключом.
- Порядок разрешения принадлежности: `match.name` → `match.nameRegex` →
  `match.path` (длиннейший префикс) → сосед по файлу.
- `overrides` — явное назначение человеком, **всегда бьёт правило**.
- Одна сущность может состоять в нескольких контейнерах: на разных осях она
  законно попадает в разные рамки.
- Принадлежность — **подсказка** (группировка в панели базы, отчёт о дрейфе). На
  геометрию видов не влияет никак.

Поля `axis` у контейнера контракт **не определяет**: ось объявляет вид (§8).
Проекты вправе проставлять его как подсказку человеку — это соглашение проекта,
которое ничем не читается.

## 7. `text.<lang>.json`

Каждое переводимое поле — **объект с происхождением**, а не строка.

```json
{
  "contractVersion": 3,
  "language": "ru",
  "entries": {
    "e_repetitionguardmiddleware": {
      "description": { "v": "Стадия Output: замечает вырождение генерации.",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" },
      "doc":         { "v": "Против цикла работают две защиты…",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" }
    },
    "rt_security": {
      "name":        { "v": "допуск", "at": "…", "origin": "authored" },
      "description": { "v": "Единственный род связи, который вправе отказать.",
                       "at": "…", "origin": "authored" }
    },
    "e_illmgateway": {
      "description": { "v": "Gateway to the model…", "at": "…",
                       "origin": "translated", "from": "ru", "fromHash": "a3f19c" }
    }
  }
}
```

### 7.1 Ключи — всё именуемое

| Префикс | Объект | Что переводится |
|---|---|---|
| `e_` | сущность | только `description`, `doc` — имя не переводится |
| `c_` | контейнер | `name`, `description`, `doc` |
| `rt_` | тип связи | `name`, `description` |
| `r_` | связь | `name` (подпись на холсте), `description`, `fromLabel`, `toLabel` |
| `v_` | вид | `name` (заголовок в каталоге и над холстом), `description`. Ключ — `id` вида целиком: он сам начинается с `v_` |

### 7.2 Поля

Разрешены шесть: `name`, `title`, `description`, `doc`, `fromLabel`, `toLabel`.

- `description` — что это, одна-две строки. Тултип, читается всегда.
- `doc` — длинный текст: причины, инварианты, что сломается при нарушении,
  ссылка на ADR. Читается по требованию.
- `fromLabel`, `toLabel` — кардинальность или роль на **концах** связи
  (ADR_20260903 §2.6): «1» у одного конца, «0..*» у другого; «owner»,
  «listener». Осмысленны только под ключом `r_*`; у остальных объектов эти
  поля просто не заполняются — каталог не знает и не обязан знать, что стоит
  за ключом, это уже прочитано выше в разделе про `name` у `r_*` (§7.1).
  Каждое — то же провенансное значение (§7.3), что и любое другое поле.

### 7.3 Происхождение

| Поле | Смысл |
|---|---|
| `v` | само значение |
| `at` | **ISO-8601 UTC с `Z`**. Локальные даты и даты без времени запрещены |
| `origin` | `authored` \| `translated` |
| `from` | язык-источник; только у `translated` |
| `fromHash` | хэш **нормализованного** текста источника на момент перевода |

Хэш считается одинаково в `core` и в редакторе (`core.Hash`): текст нормализуется
(CRLF → LF, хвостовые пробелы и табуляции убираются, три и более переносов подряд
схлопываются в два, обрезка по краям), затем FNV-1a 32 бит по **UTF-16 code
units**, результат — 8 шестнадцатеричных цифр в нижнем регистре.

### 7.4 Три состояния и одна проверка

| Состояние | Условие | Действие |
|---|---|---|
| свежий | `fromHash` == хэш текущего значения `from` | ничего |
| протух | `fromHash` != хэш текущего значения `from` | перевести заново |
| разошлись | оба значения `authored`, ни одно не ссылается на другое | конфликт, решает человек |

**Хэш решает, дата информирует.** Порядок по времени в проверках не участвует:
часы врут, коммиты переставляются, «позже» не значит «новее по смыслу».

**Гранулярность — поле.** Правка `name` не протухляет `doc`.

**Фолбэка нет.** Отсутствие ключа в языке — недостача, а не норма: правило v2
«отсутствующий ключ — фолбэк на базу» отменено. Как рендер поступает с
отсутствующим текстом при показе — его дело; в отчёте это всё равно дыра.

**Правка человеком делает значение `authored`** и снимает `from`/`fromHash`.

### 7.5 Чтение v2-файлов

Каталог со строками вместо объектов читается: значения загружаются **без
происхождения вовсе**, а не с придуманным `authored`. Приписать авторство
тексту, чьё происхождение никто не записывал, значило бы показать чистую
ведомость там, где её нет.

## 8. `views/<view_id>.view.json`

```json
{
  "id": "v_semantic_atlas",
  "project": "core",
  "axis": "axis_subsystem",
  "icon": "🗺️",
  "relations": { "default": "visible", "except": ["r_gateway_repguard"] },
  "zones": [
    { "id": "z_llm_middleware", "container": "c_llm_middleware", "parent": "z_llm",
      "x": -1120, "y": 1480, "width": 900, "height": 1040, "styleId": "zone.green" }
  ],
  "nodes": [
    { "entity": "e_repetitionguardmiddleware", "zone": "z_llm_middleware",
      "x": -950, "y": 1600, "width": 210, "height": 60, "styleId": "node.class" }
  ]
}
```

### 8.1 `axis` — обязательное поле

Объявляет, **что классифицирует вложенность блока в рамку** на этом виде:
`axis_layer`, `axis_subsystem`, `axis_security_zone`, `axis_process`,
`axis_turn`… Множество открытое, имена задаёт проект.

Без оси узел внутри прямоугольника нечитаем: «живёт в этой сборке», «работает в
этом процессе» и «подвинут, чтобы стрелки не пересекались» выглядят одинаково.

- Вид без `axis` наследует `project.defaultAxis`.
- Нет ни того, ни другого — **схема всё равно открывается**, редактор показывает
  баннер, а вложенность в ней ничего не утверждает и не проверяется. Отказ
  открывать был бы хуже: устаревший файл делал бы проект недоступным.
- Два вида на **разных** осях вправе класть один узел в разные контейнеры. Два
  вида на **одной** оси — нет: это противоречие модели.

Имя файла — `<id>.view.json`; `id` внутри, если есть, главнее имени файла. `id` вида можно
сменить: файл, ключ текста во всех языках и `defaultView` переписываются вместе
([`ADR_20260923-8`](adr/ADR_20260923-8_contract_project-and-view-ids-can-change.md)). Необязательные
`icon`, `theme`, `order` задают строку вида в каталоге (как у проекта, §2). Имени в файле нет —
оно в `text.<lang>.json` под `id` вида (§7.1).

### 8.2 Зоны и размещения

| Поле зоны | Смысл |
|---|---|
| `id` | префикс `z_` |
| `container` | контейнер, который зона показывает; `null` для декоративной рамки |
| `parent` | вложенность **зон на этом виде**; может отличаться от иерархии контейнеров |
| `x`,`y`,`width`,`height`,`styleId` | геометрия и стиль |

| Поле размещения | Смысл |
|---|---|
| `entity` | какую сущность ставим |
| `zone` | в какой зоне; `null` — вне любой рамки, это законно |
| `x`,`y`,`width`,`height`,`styleId` | геометрия и стиль |

Правила:

1. **Вид — выборка.** Сущность попадает на холст только вытаскиванием из
   реестра. Зоны «НЕ РАЗМЕЩЕНО» не существует.
2. **Принадлежность записана явно**, из геометрии не выводится. Блок внутри
   рамки, но с `zone: null`, легален.
3. **Координаты правит человек.** Утилита и скрипт «для восстановления» в `views/`
   не пишут никогда. Агент пишет геометрию только по прямой просьбе человека и только
   в пределах поручения, не затирая чужую раскладку
   ([`ADR_20260924`](adr/ADR_20260924_contract_agent-lays-out-views-on-request.md);
   как устроен вид — [`LAYOUT.md`](LAYOUT.md)).

### 8.3 Совместимость имён

Загрузчик принимает оба написания; **писать следует левое**, редактор сохраняет
именно его:

| Писать | Также принимается |
|---|---|
| `nodes` | `placements` |
| `entity` | `id` |
| `zone` | `container` |

### 8.4 Имя зоны ищется по двум ключам

Текст зоны берётся по её собственному `id`, а при промахе — по `c_` + хвост
`z_`: зона `z_llm_middleware` подхватит запись контейнера `c_llm_middleware`.
Соглашение об именах здесь несущее, а не косметическое.

### 8.5 Видимость связей

Три механизма, по убыванию дешевизны:

1. **Правило обоих концов** — ничего не хранит. Связь видна, только если на виде
   есть **обе** её сущности. Следствие, не настройка; съедает основную массу.
2. **`relations.default`** — что делать со связью, по которой решения не
   принимали: `visible` для рабочих видов, `hidden` для обзорных.
3. **`relations.except`** — поимённые решения, противоположные умолчанию. Всегда
   меньшая сторона списка.

Политики по типу связи **нет** и не будет: типы — открытое множество, новый тип
при такой политике оказался бы в неопределённом состоянии.

**Ключ `edges` в виде.** Массив рёбер переопределяет реестр целиком: `[]`
означает «рёбер нет», а не «взять все связи». Чтобы вид показывал связи проекта,
`edges` надо **опустить**.

**`routing` на ребре вида** — override режима роутинга для одной связи на одном
виде (ADR §2.7). Хранится только выбор (`bezier` \| `orthogonal` \|
`tree-horizontal` \| `tree-vertical`); вычисленная ломаная **не хранится
никогда** — роутер чистая функция от портов и препятствий, пересчитывается на
каждой перерисовке. Каскад — §11.3.

## 9. Инварианты, которые обязан держать любой писатель файлов

1. `id` сущности не меняется никогда; переименование — только `name`.
2. Текст живёт в каталогах текстов. В `relations.json` подписей нет, в
   `entities.json` описаний нет.
3. Имя сущности не переводится.
4. `at` — всегда UTC с `Z`.
5. Правка значения человеком делает его `authored` и снимает `from`/`fromHash`.
6. В `views/` пишет редактор по действию человека и агент по прямой просьбе человека;
   утилиты — никогда (§8.2 п. 3).

## 10. Что контракт объявляет, но код пока не делает

Спецификация описывает формат; часть проверок формата ещё не реализована. Список
держится здесь, чтобы никто не строил планы на несуществующее — подробности и
рабочие обходы пока не записаны.

- **Проверка протухания переводов (§7.4) не реализована.** Хэши никто не считает:
  редактор намеренно не переводит, а переводящей утилиты нет. Три состояния
  сегодня различает только человек.
- **Противоречие двух видов на одной оси (§8.1) не проверяется.**
- **`containers.json` редактор не читает** — связь зоны с контейнером держится на
  соглашении об именах (§8.4).
- **Сверка с кодом запускается руками по готовому файлу фактов**
  (`semaps sync --facts`, [`EXTRACTOR.md`](EXTRACTOR.md) §5): хост пока не зовёт
  извлекатель сам, кнопки в редакторе нет.

## 11. Оформление блока: `shape`, `template`, роутинг

Три независимые оси блока — контур, стиль и содержимое —
[`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md)
§2.1. Поля `shape` и `template` объявлены не в этом контракте, а в
`styles.json` — этот раздел
только сводит их вместе с реестрами, которые они адресуют.

### 11.1 `shape` — контур

Поле блочного стиля, значения: `rect` (умолчание) \| `ellipse` \| `diamond` \|
`cylinder` \| `hexagon` \| `actor`. Отдельного override на размещении контракт
не резервирует — задавать форму per-node следует отдельным стилем (пример —
`usecase`, `store`, `decision`, `stage`, `actor` в `styles.json`), как и для
цвета.

### 11.2 `template` — содержимое

Поле блочного стиля: `id` записи из
`templates.json`.
Формат реестра — массив шаблонов, у каждого `id`, `name`, необязательный
`description` и `lines` (текст шаблона, построчно — так диффы остаются
построчными, компилированное дерево в файл не попадает никогда, ADR §2.3):

```json
{ "id": "class", "name": "Класс / интерфейс",
  "lines": ["@Name", "@Members([name, type], where=kind:field)"] }
```

**Язык шаблона** (ADR §2.3): перенос строки — вертикальный стек, `|` внутри
строки — колонки, `@Directive(позиционный, имя=значение)`. Директивы первой
очереди — `@Name`, `@Description`, `@Members([поля], where=kind:…)`,
`@Asset(имя, h=…, w=…)`. Пустая секция ничего не рисует и не занимает места.

**Каскад назначения**, от частного к общему: размещение → стиль → встроенный
дефолт `title-only` («только заголовок»). Отсутствие значения означает
наследование дальше по цепочке.

### 11.3 `routing` — форма линии связи

Значения: `bezier` (умолчание, текущая кривая) \| `orthogonal` \|
`tree-horizontal` \| `tree-vertical`. Хранится только выбор режима —
вычисленная ломаная не сохраняется нигде (ADR §2.7, и §8.5 выше).

**Каскад выбора**, от частного к общему: `routing` на ребре вида (§8.5) →
`routing` вида целиком → `routing` стиля связи (`styles.json`, ключ — `id`
типа связи, например `extends`, `call`) → встроенный дефолт `bezier`. Уровень
«тип связи» делает основную работу: у большинства рёбер `routing` вообще не
задан ни на ребре, ни на виде.

### 11.4 Реестр содержимого (`@Asset`)

`content/index.json` —
манифест картинок для директивы `@Asset(имя, …)`:

```json
{ "assets": [
  { "id": "brain", "name": "Мозг", "file": "content/brain.svg",
    "description": "Обобщённая «думающая» сущность." } ] }
```

Сами файлы (`content/*.svg`) лежат рядом с манифестом и раздаются как обычная
статика. Перед вставкой в DOM SVG **обязательно санируется** — белый список
элементов и атрибутов, без `<script>`, обработчиков событий и внешних ссылок
(`editor/src/assets/sanitizeSvg.ts`); картинки приносят откуда
попало, а рисуются внутри привилегированного окна редактора.
