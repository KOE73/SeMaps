# Формат проектов SeMaps — контракт v5

Нормативное описание того, **что считается корректным файлом модели на диске**.

Принят [`ADR_20260831_diagrams_text-provenance-and-view-axes`](adr/ADR_20260831_diagrams_text-provenance-and-view-axes.md),
развивает [`ADR_20260828_diagrams_model-contract-v2`](adr/ADR_20260828_diagrams_model-contract-v2.md).
v5 — словарь типов, контейнер — это сущность, вид — один массив размещений:
[`ADR_20260927-6`](adr/ADR_20260927-6_contract_v5-kinds-and-containers.md); стиль принадлежит типу:
[`ADR_20260927-7`](adr/ADR_20260927-7_contract_style-belongs-to-a-type.md), и типу связи —
[`ADR_20260930-2`](adr/ADR_20260930-2_contract_edge-style-belongs-to-a-relation-type.md); тип связи, как тип
сущности, — строка, всё о нём в словаре, файла типов у проекта нет:
[`ADR_20260930-6`](adr/ADR_20260930-6_contract_relation-types-live-in-the-dictionary.md);
принадлежность контейнеру в графе берётся из связей `contains`:
[`ADR_20260930`](adr/ADR_20260930_contract_graph-containers-from-contains.md).
Реализации в коде — `code[]` у сущности и `evidence[]` у связи, форма взята у забытой ветки
([`ADR_20260927-2`](adr/ADR_20260927-2_contract_entity-is-intent-code-is-realizations.md)) без её сверки по языкам:
[`ADR_20260930-4`](adr/ADR_20260930-4_contract_code-shape-now-multi-language-later.md). Имя нарисованной сущности — текст под её `id`:
[`ADR_20260930-5`](adr/ADR_20260930-5_contract_authored-entity-name-is-text.md). Версии 4 в этой линии нет: обе формы — часть v5.
Старую форму загрузчик не читает, а называет
([`ADR_20260927-3`](adr/ADR_20260927-3_core_migrations-outside-the-loader.md)); переписывает её
`semaps migrate` ([`ADOPTING.md`](ADOPTING.md)).

## 1. Структура проекта на диске

```
<workspace>/projects/<project_id>/
  project.json          манифест
  entities.json         каталог сущностей
  relations.json        каталог связей
  text.<lang>.json      тексты с происхождением по полям
  views/
    <view_id>.view.json вид: ось, геометрия, размещения
```

`containers.json` в контракте нет: контейнер — сущность (§6, §8.2). `relation-types.json` тоже нет:
тип связи — строка на связи, всё о нём в словаре (§5, §6). Встретив любой из двух, загрузчик и
`semaps check` называют файл.

Стили общие для всех проектов: `<workspace>/styles.json`, а если его нет — умолчание инструмента
[`host/defaults/styles.json`](../host/defaults/styles.json). То же для `templates.json` и `content/`
и для `canvas.json` — чисел холста (сетка, размеры блока и контейнера, заголовок и отступ контейнера, зазоры):
`<workspace>/canvas.json`, а если его нет — [`host/defaults/canvas.json`](../host/defaults/canvas.json).
Словарь типов `kinds.json` (§6) тоже общий, но не заменяет умолчание, а **дополняет** его.
Форма `canvas.json`: `{"grid":10,"node":{"width","height","minWidth","minHeight","radius"},"container":{"minWidth","minHeight","headerHeight","padding","radius"},"gap":{"node","container"}}`
(до v5 ключ назывался `zone`; загрузчик его не читает, `semaps check` называет),
единицы — единицы модели (1 единица = 1 пиксель экрана при масштабе 1). Это единственное место,
где числа записаны: хост (`get_view`, `layout_guide`, геометрические инструменты) и редактор читают
один файл. Сетка — привычка редактора; **хост к сетке не привязывает**.
Рядом с ним — ещё два общих реестра, оба введены
[`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md):
`templates.json` (шаблоны содержимого
блока) и `content/index.json`
(картинки для директивы `@Asset`, файлы `content/*.svg` лежат рядом). Оба формата — §11.

**Перечня видов нет** ([`ADR_20260923-7`](adr/ADR_20260923-7_contract_projects-and-views-found-not-listed.md)).
Проект — любая папка `projects/<id>/`, в которой есть `project.json`; вид — любой файл
`views/*.view.json` в ней. Каталог в редакторе двухуровневый: проекты, в них виды. Пустой
workspace (нет даже `projects/`) законен. Файл `catalog.json` упразднён: он не читается, а
`semaps check` сообщает о нём как об устаревшем.

**Базового языка нет.** Каталоги текстов равноправны; направление перевода
записано на каждом значении отдельно (§7).

## 2. `project.json`

```json
{
  "id": "core",
  "title": "Core Layer (src/core)",
  "subtitle": "Domain, MCP, Security, Host",
  "contractVersion": 5,
  "defaultView": "v_semantic_atlas",
  "defaultAxis": "axis_subsystem",
  "languages": ["ru"],
  "icon": "brain",
  "sources": { "include": ["src/core"] }
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | совпадает с именем каталога |
| `title` | да | заголовок проекта; не переводится. Нет — в каталоге показывается `id` |
| `subtitle` | нет | вторая строка в каталоге |
| `contractVersion` | да | `5`. Ниже — загрузчик отвечает ошибкой, называющей файл, поле и версию ([`ADR_20260927-3`](adr/ADR_20260927-3_core_migrations-outside-the-loader.md)); эту версию нельзя сменить операцией — её меняет только `semaps migrate` |
| `defaultView` | нет | `id` вида, который редактор открывает первым; операция создания вида с `setDefault` переписывает его (`core/create.go`) |
| `defaultAxis` | нет | ось для видов, не объявивших свою (§8) |
| `languages` | нет | какие `text.<lang>.json` грузить; первый — основной для показа |
| `icon`, `theme`, `order` | нет | строка проекта в каталоге: значок, цветовая тема значка, место (по `order`, затем по `id`). `icon` — **ключ реестра иконок** редактора: имя иконки Tabler из его набора (`folder`, `brain`, `flask`…; набор — `editor/src/ui/iconSet.ts`, его же предлагает выбор иконки) или вид символа/связи (`class`, `extends`…). Неизвестное значение, в том числе эмодзи, рисуется одной запасной иконкой ([`ADR_20260929_editor_icons-are-registry-keys`](adr/ADR_20260929_editor_icons-are-registry-keys.md)). Так же устроен `icon.glyph` стиля блока в `styles.json` |
| `sources.include` | нет | пути от корня исходников: сверка берёт в проект только символы из них (внешние символы — всегда); нет — весь корень |

`id` проекта можно сменить: папка переименовывается, `project` в каждом виде переписывается
([`ADR_20260923-8`](adr/ADR_20260923-8_contract_project-and-view-ids-can-change.md)).

Поля `views` в контракте больше нет: виды — это файлы в `views/` (§1). Встретив его, считать
мусором.

Поля `baseLanguage` в v3 **нет**. Встретив его, считать мусором: направление
перевода задаётся не здесь.

## 3. `entities.json`

```json
{
  "entities": [
    {
      "id": "e_repetitionguardmiddleware",
      "name": "RepetitionGuardMiddleware",
      "kind": "class",
      "origin": "code",
      "status": "present",
      "namespace": "Acme.Agent.Guards",
      "code": [
        { "lang": "csharp", "ref": "src/Acme.Agent/Guards/RepetitionGuardMiddleware.cs",
          "symbol": "Acme.Agent.Guards.RepetitionGuardMiddleware" }
      ],
      "members": []
    },
    {
      "id": "e_storage",
      "kind": "subsystem",
      "origin": "authored",
      "status": "present",
      "code": [{ "ref": "docs/storage.md" }]
    }
  ]
}
```

Имя второй сущности, нарисованной, — в `text.<lang>.json` под её `id` (§7): в `entities.json` у неё `name` нет.

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | префикс `e_`. Выдаётся **один раз и не меняется никогда**, включая переименование |
| `name` | у `code` и без `origin` | имя типа из кода, **не переводится**, в текстах его нет. У `origin: authored` поля **нет**: имя нарисованной сущности — текст `name` под её `id` в `text.<lang>.json` (§7.1), правится свободно, `id` при этом не меняется. Пакет, что несёт `name` у `authored`, правило записи отвергает, а файл с таким полем загрузчик и `semaps check` называют старой формой ([`ADR_20260930-5`](adr/ADR_20260930-5_contract_authored-entity-name-is-text.md)). Что показать, когда имени нет в языке: имя другого языка проекта (в порядке `languages`), иначе `id` |
| `kind` | да | тип из словаря `kinds.json` (§6): из кода — `nativeKind` символа (`class`, `namespace`, `assembly`…), руками — архитектурный (`app`, `database`, `subsystem`…). Тип вне словаря допустим, `semaps check` о нём сообщает. Тип с `container: true` делает сущность **контейнером** (§8.2) |
| `origin` | нет | `code` \| `authored`. v2-шное `manual` переименовано в `authored`. От него зависит, где имя (`name`, выше) |
| `status` | нет | `present` \| `missing` \| `planned`. Сохранённые записи не удаляются (§9 п. 7): ушедшая сущность сохраняет `id` для ссылок |
| `namespace` | нет | пространство имён / пакет из кода |
| `code` | нет | реализации в коде, от нуля до N, по одной на язык (ниже). Нет кода — нет ключа, не `[]`. `codeRef` и `symbol` верхнего уровня упразднены |
| `members` | нет | члены типа, для директивы `@Members` шаблона содержимого (§11.2) |

**Запись `code[]`** — одна реализация сущности
([`ADR_20260930-4`](adr/ADR_20260930-4_contract_code-shape-now-multi-language-later.md), форма — [`ADR_20260927-2`](adr/ADR_20260927-2_contract_entity-is-intent-code-is-realizations.md)):

| Поле | Обяз. | Смысл |
|---|---|---|
| `lang` | вместе с `symbol` | язык — `language` фактов извлекателя: `csharp`, `typescript`, `go` |
| `ref` | нет | файл от корня исходников (`source_root`), для просмотра кода и `semaps check`; якорь `#…` или `:строка` допустим. Запись с `symbol` без `ref` — реализация **внешнего символа** (`io.Writer`, [`ADR_20260927-4`](adr/ADR_20260927-4_contract_external-symbols.md)): файла нет, кнопки кода нет |
| `symbol` | вместе с `lang` | `id` символа в фактах извлекателя ([`EXTRACTOR.md`](EXTRACTOR.md) §2.1, форма — [`ADR_20260923-5`](adr/ADR_20260923-5_extractors_symbol-ids.md)). Ключ, по которому `semaps sync` узнаёт сущность на следующем прогоне; ставит его сверка. Человек правит его в одном случае — подтверждая переименование в коде (EXTRACTOR §5) |
| `status` | нет | `missing` — символ пропал из фактов своего языка; допустимо, но сверка сегодня его не ставит |

Запись должна иметь `ref` или `symbol`. Запись только с `ref` — ручная ссылка на файл (`.csproj`, схема БД, документ). На один
язык — не больше одной записи. У сущности `authored` `code` допустим (нарисовал — потом привязал к файлу), но сверка её не
сопоставляет с символами. `namespace` остаётся полем сущности, выведенного из `symbol` нет; `native` в записи нет
(`ADR_20260930-3` §4).

**Сверка ведёт одну реализацию за прогон.** Прогон извлекателя языка L меняет только запись `code[]` с `lang: L` и пишет
её: `lang`, `ref`, `symbol`. Сущность, реализованная только на другом языке, для него не существует: не `missing`, не
усыновляется, не трогается. Привязка второго языка к уже существующей сущности, выведенные статусы, неизменный `origin` —
не сделано, ждёт проекта, которому это нужно (ADR_20260930-4 §4).

**Инвариант:** `id` уникален в проекте. Переименование типа из кода — правка `name` при неизменном `id`; ни один
другой файл при этом не меняется. Пара `(lang, symbol)` уникальна среди не-`authored` записей `code[]`, и у сущности не
больше одной записи на язык: иначе реестр противоречит себе, `sync` не пишет ничего.

Сущность от символа `module` (сборка, пространство имён, файл) — обычная сущность:
`kind` — `nativeKind` символа (`assembly`, `namespace`, `file`); эти типы — контейнеры по
словарю, а связь `contains` сверки (§4) — то, что кладёт в них другие сущности.

**Форма `members`** ([`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md)
§2.4): массив объектов, каждый — один член типа.

```json
"members": [
  { "kind": "field", "name": "Retries", "type": "int", "visibility": "private" },
  { "kind": "method", "name": "InvokeAsync",
    "type": "Task<LlmTurnResult>", "visibility": "public",
    "note": "точка входа middleware" }
]
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `kind` | нет | открытая строка: `field`, `property`, `method` — то, что фильтрует `where=kind:…` в шаблоне; без него член просто не попадёт под такой фильтр |
| `name` | да | имя члена |
| `type` | нет | тип поля/свойства или сигнатура возврата метода |
| `visibility` | нет | `public` \| `private` \| … — открытая строка, используется и фильтром, и значком (замок у `private` задаётся в стиле, не в данных) |
| `note` | нет | короткая пометка, не переводится |

Разница между полем класса и колонкой БД — это значение `type`, а не отдельная
форма записи: `@Members` в шаблоне общий для обоих случаев (ADR §2.4).

Члены — только объекты; строчная форма старых реестров контрактом не поддерживается.

## 4. `relations.json`

```json
{
  "contractVersion": 5,
  "relations": [
    { "id": "r_repguard_illmmiddleware_implements",
      "from": "e_repetitionguardmiddleware", "to": "e_illmmiddleware",
      "type": "implements", "origin": "code", "status": "present",
      "evidence": [{ "lang": "csharp", "ref": "src/Acme.Agent/Guards/RepetitionGuardMiddleware.cs",
                     "symbol": "Acme.Agent.Guards.RepetitionGuardMiddleware" }] },
    { "id": "r_controller_outcome_holds_activeRuns",
      "from": "e_vmcontroller", "to": "e_vmrunoutcome",
      "type": "holds.many", "origin": "code", "status": "present",
      "evidence": [{ "lang": "csharp", "ref": "src/VM/VmController.cs", "symbol": "VM.VmController",
                     "via": { "member": "activeRuns", "memberKind": "field", "modifiers": ["private", "readonly"],
                              "text": "ConcurrentDictionary<long, Task<VmRunOutcome>>", "path": ["value", "result"],
                              "cardinality": "keyed", "mutability": "mutable", "deferred": true } }] }
  ]
}
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `id` | да | префикс `r_`. Порождённая связь: `r_<from>_<to>_<type>` (без префиксов) для органических рёбер; членская связь: `r_<from>_<to>_<member>[_<path>]`, коллизия — `_2` |
| `from`, `to` | да | `id` сущностей |
| `type` | да | тип связи: слово без пробелов. Что оно значит — в словаре (§6, `relationGroups`); тип вне словаря допустим, `semaps check` о нём сообщает (§5) |
| `origin` | нет | `code` \| `authored` |
| `status` | нет | `present` \| `missing` |
| `evidence` | нет | реализации связи в коде — проверяемое основание, от нуля до N, по одной на язык (ниже). Нет оснований — нет ключа. `via` верхнего уровня упразднён |

**Запись `evidence[]`** — та же форма, что запись `code[]` сущности (§3: `lang` и `symbol` вместе, `ref`, `status`;
`symbol` и `ref` — символ и файл конца `from`, у внешнего символа `ref` нет), и ещё:

| Поле | Обяз. | Смысл |
|---|---|---|
| `via` | нет | подпись членской связи в этом языке: `member`, `memberKind`, `modifiers`, `text`, `path`, `cardinality`, `mutability`, `deferred` (все необязательны); есть только у членских связей (`kind` в фактах — `holds`, `uses`, `injects`). Подпись связи — `via` первой записи, у которой он есть. Запись может состоять из одного `via` |

Запись должна иметь `ref`, `symbol` или `via`; номер строки — якорь `:N` в `ref`, `codeRef` и `line` упразднены.
`native` ребра фактов (как язык выразил связь) в реестр не пишется: он для показа и фильтров, тип связи по нему не выводится
([`ADR_20260930-3`](adr/ADR_20260930-3_contract_fact-kinds-and-derived-relation-types.md)). Как у сущности, `sync` пишет одну запись
за прогон — языка своих фактов ([`ADR_20260930-4`](adr/ADR_20260930-4_contract_code-shape-now-multi-language-later.md)).

Порождённые сверкой типы из органических рёбер: `extends`, `implements`, `contains`
(вложенность: сборка / пространство имён / файл содержит тип, тип — вложенный тип),
`depends` (сборка зависит от сборки). Членские связи: `holds.one`, `holds.optional`,
`holds.many`, `holds.many.ro`, `holds.keyed`, `holds.keyed.ro` (через открытый член),
те же с суффиксом `.internal` (через непубличный член), `injects` (конструктор),
`uses` (остальное). Реестр знает все связи; какие показать, решает вид (§8.5).

**`contains` — принадлежность контейнеру.** Связь `contains` от сущности-контейнера (тип
которой `container: true`, §6) к другой сущности говорит, что вторая лежит в первой. Её пишет
сверка (сборка, пространство имён, файл — и вложенный тип) или человек, как любую авторскую
связь (`add_relation`); других источников принадлежности нет — ни правил по имени и пути, ни
соседа по файлу. Это принадлежность **в реестре и в графе кода**
([`ADR_20260930_contract_graph-containers-from-contains`](adr/ADR_20260930_contract_graph-containers-from-contains.md)):
из двух несвязанных контейнеров, содержащих одну сущность, граф не выбирает — сущность
не относится ни к одному. Вложенность на виде — не она, а `parent` размещения (§8.2).

**`label` в v3 удалён.** Весь текст связи живёт в `text.<lang>.json` под её `id`;
фолбэка на структуру нет. Связь без текстовой записи рисуется без подписи — это
видно, и так и задумано.

**Подписи на концах** (`fromLabel`, `toLabel` — кардинальность, роль: «1»,
«0..*», «owner») живут там же, под тем же `id`, наравне с `name` (см. §7.2).
**У связи с `origin: "code"` текста нет вовсе** — ни `name`, ни `fromLabel`,
ни `toLabel`: `sync` перепишет его при каждом прогоне, а смысл несёт `type`
(см. §7.4, «фолбэка нет»).

## 5. Типы связей

Файла типов связей у проекта **нет**
([`ADR_20260930-6`](adr/ADR_20260930-6_contract_relation-types-live-in-the-dictionary.md)): тип связи
устроен как тип сущности. Это строка `type` на связи (§4), а всё о типе — имя и описание по языкам,
базовый стиль, умолчание видимости — запись словаря `kinds.json` (§6, раздел `relationGroups`), общего
для рабочего пространства. `origin` у типа нет: его несёт каждая связь. Имени и описания в текстах проекта
нет: ключей `rt_<id>` контракт не знает (§7.1). Поля `styleId` у типа связи тоже нет: стиль принадлежит типу
и назван в `forKinds` самого стиля (§11.5).

Проект со старым `relation-types.json` загрузчик и `semaps check` называют ошибкой с именем файла;
переписывает проект `semaps migrate` ([`ADOPTING.md`](ADOPTING.md)): файл и ключи `rt_` удаляются, а то,
чего словарь ещё не говорит, — `visibility`, имя, описание, тип вне словаря — переносится записью в
`kinds.json` рабочего пространства.

**Типы из кода.** Сверка выводит их из `kind` (органическое ребро) и признаков в `via`
(членская связь) и пишет в `type` связи; больше она ничего не пишет. Базовый словарь описывает их все, с
такой видимостью по умолчанию:

| Ребро в фактах | Видимость | Смысл |
|---|---|---|
| `extends`, `implements`, `contains`, `depends` | видим | органические связи, выводятся прямо из `kind` |
| `holds.one`, `holds.optional`, `holds.many`, `holds.many.ro`, `holds.keyed`, `holds.keyed.ro` | видим | открытый элемент члена (публичный или по иерархии доступа). Вариант без суффикса — «не известно» не выводит отдельный тип |
| те же с суффиксом `.internal` | скрыт | то же, но внутренний элемент (приватный или ограниченный доступ) |
| `injects` | скрыт | ребро `uses` с `via.memberKind: constructor` |
| `uses` | скрыт | параметр, возвращаемое значение, сигнатура или правая часть типа-псевдонима |

Авторские типы базового словаря (`call`, `data-flow`, `event`, `storage`, `runs`, `security`, `realizes`,
`composes`) умолчания видимости не имеют: решает вид. Тип `references` — устаревший: он есть в словаре
только ради старых реестров, сверка его не пишет, а такие связи помечает `missing` (пишется `depends`). `visibility` (`visible` \| `hidden`, необязательно)
— умолчание для связей этого типа на виде (§8.5); нет — решает вид. Оно **одно на рабочее пространство**,
а не на проект: рабочее пространство меняет его записью с тем же `id` в своём `kinds.json` (§6).

Множество типов **открыто**: проверки «такого типа не бывает» нет, связь может иметь любой тип — слово без
пробелов. Тип, которого нет в словаре, законен, но у него нет ни описания, ни базового стиля, ни умолчания
видимости: он показывается своим `id`, связь рисуется стилем `default.edge`, а `semaps check` перечисляет такие
типы («тип связи не из словаря»). Новый тип описывает запись в `kinds.json` рабочего пространства (§6); отдельного
инструмента и отдельного файла для этого нет.

## 6. `kinds.json` — словарь типов

Общий для рабочего пространства, рядом со `styles.json`. Инструмент поставляет базовый
словарь [`host/defaults/kinds.json`](../host/defaults/kinds.json); `<workspace>/kinds.json`
его **дополняет**: новые группы и записи добавляются в конец, группа или запись с уже известным
`id` заменяет прежнюю целиком (запись уходит из старой группы). В словаре два раздела с одним
устройством: **типы сущностей** (`groups`) и **типы связей** (`relationGroups`).

В базовом словаре только то, что приносят извлекатели по нормативным таблицам
[`docs/extractors/*.md`](extractors/) (`class`, `interface`, `struct`, `record`, `record-struct`,
`enum`, `delegate`, `namespace`, `assembly`, `package`, `module`, `file` и остальные
`nativeKind` всех поддерживаемых языков), типы связей, которые выводит сверка (§5), и
нейтральные архитектурные понятия (`component`, `service`, `actor`, `store`, `group`…). Всё,
что подогнано под один проект, — в `kinds.json` этого проекта.

```json
{
  "contractVersion": 5,
  "groups": [
    { "id": "structure",
      "name": { "ru": "Контейнеры", "en": "Containers" },
      "description": { "ru": "Рамки схемы.", "en": "The frames of a diagram." },
      "kinds": [
        { "id": "subsystem", "container": true, "style": "subsystem",
          "name": { "ru": "Подсистема", "en": "Subsystem" },
          "description": { "ru": "Крупная часть системы со своей ответственностью.", "en": "…" } } ] } ],
  "relationGroups": [
    { "id": "relations.flow",
      "name": { "ru": "Связи схемы", "en": "Diagram relations" },
      "types": [
        { "id": "data-flow", "style": "data-flow", "visibility": "visible",
          "name": { "ru": "поток данных", "en": "data flow" },
          "description": { "ru": "Данные идут от одной части к другой.", "en": "…" } } ] } ]
}
```

| Поле типа сущности | Обяз. | Смысл |
|---|---|---|
| `id` | да | значение `kind` сущности. Уникален во всём словаре, не только в группе |
| `name` | да | имя по языкам; нет нужного языка — берётся любой имеющийся (первый по коду) |
| `description` | нет | что это, одной-двумя фразами. Для человека в подсказке и для агента в `get_kinds` |
| `container` | нет | `true` — сущность этого типа **контейнер**: рисуется рамкой и может держать другие размещения (§8.2), а в графе кода держит сущности, которые содержит связью `contains` (§4) |
| `style` | нет | базовый стиль типа; нет — стиль с `id`, равным типу (§11.5) |

| Поле типа связи | Обяз. | Смысл |
|---|---|---|
| `id` | да | значение `type` связи. Уникален во всём словаре |
| `name`, `description` | `name` да | как у типа сущности |
| `style` | нет | базовый стиль типа связи; нет — стиль с `id`, равным типу (§11.5) |
| `visibility` | нет | `visible` \| `hidden` — что вид показывает из связей этого типа, по которым решения не принимали (§8.5); нет — решает вид. Основа — умолчание `host/defaults/kinds.json` (§5); запись рабочего пространства с тем же `id` заменяет её целиком, в том числе `visibility` |

У группы обоих разделов — `id`, `name`, необязательный `description` и список записей (`kinds`,
`types`). Группа отвечает на вопрос «откуда это» (код, архитектура, поведение), признак
`container` — «рисуется ли рамкой»: `namespace` из группы кода — тоже контейнер.

**Словарь — не enum.** Тип вне словаря не ошибка: сверка пишет `nativeKind` любого языка, проект
заводит свои типы. `semaps check` перечисляет типы сущностей и типы связей «не из словаря»;
MCP `get_kinds` отдаёт словарь и то, что проект использует сверх него.

**Контейнер — роль типа, а не отдельный вид объектов.** `namespace`, `package`, `subsystem`,
`layer`, `group` — разные типы с `container: true`. Контейнер — обычная сущность
`entities.json` со своими происхождением, статусом, кодом, текстами (§8.2); файла контейнеров
нет. Принадлежность сущности контейнеру в реестре и в графе кода — связь `contains` (§4).
Из-за неоднозначности («два несвязанных контейнера содержат одно») принадлежности нет
вовсе: ничего не угадывается.

## 7. `text.<lang>.json`

Каждое переводимое поле — **объект с происхождением**, а не строка.

```json
{
  "contractVersion": 5,
  "language": "ru",
  "entries": {
    "e_repetitionguardmiddleware": {
      "description": { "v": "Стадия Output: замечает вырождение генерации.",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" },
      "doc":         { "v": "Против цикла работают две защиты…",
                       "at": "2026-08-31T14:22:05Z", "origin": "authored" }
    },
    "e_illmgateway": {
      "description": { "v": "Gateway to the model…", "at": "…",
                       "origin": "translated", "from": "ru", "fromHash": "a3f19c" }
    }
  }
}
```

### 7.1 Ключи — всё именуемое

Тип связи ключа не имеет: его имя и описание — в словаре (§5, §6). Ключей `rt_` нет: загрузчик их не
читает, запись отвергает, `semaps check` называет такой ключ.

| Префикс | Объект | Что переводится |
|---|---|---|
| `e_` | сущность | `description`, `doc`; у сущности `origin: authored` ещё и `name`. Имя сущности из кода не переводится: оно в `entities.json`, в текстах его нет |
| `r_` | связь | `name` (подпись на холсте), `description`, `fromLabel`, `toLabel` |
| `v_` | вид | `name` (заголовок в каталоге и над холстом), `description`. Ключ — `id` вида целиком: он сам начинается с `v_` |

**Имя нарисованной сущности** ([`ADR_20260930-5`](adr/ADR_20260930-5_contract_authored-entity-name-is-text.md)) — текст `name` под
её `e_`-ключом, по языкам, с провенансом, как у остальных текстов; в `entities.json` у неё `name` нет. Экран показывает `id`
и имя; имя правится свободно (правка текста, в панели «Изменения» — правка текста под `id` сущности), `id` не меняется. Нет
имени в основном языке проекта (первый в `languages`) — показывается имя другого языка (в порядке `languages`), иначе `id`;
для имён нарисованных сущностей это и есть фолбэк (правило §7.4 «фолбэка нет» к ним не относится). Пустое имя не пишется.
Пакет, создающий нарисованную сущность, несёт её `name` хотя бы в одном языке; `name` под ключом сущности из кода правило
записи отвергает, `title` под `e_`-ключом не бывает никогда. Проверка `semaps check` называет недостачу, только когда имени
нет ни в одном языке, и «лишнее имя» — текст `name` под ключом сущности из кода, который никто не читает.

Контейнер — сущность, поэтому его подпись — то же имя: текст `name` под его `e_`-ключом (если он нарисован; `namespace` из
кода назван в `entities.json`), а описание и `doc` — там же, как у любой сущности. Ключей `c_` и `z_` нет: загрузчик их не
читает, `semaps check` называет такой ключ.

### 7.2 Поля

Разрешены шесть: `name`, `title`, `description`, `doc`, `fromLabel`, `toLabel`.

- `description` — что это, одна-две строки. Тултип, читается всегда.
- `doc` — длинный текст в **Markdown**: причины, инварианты, что сломается при
  нарушении, ссылка на ADR. Читается по требованию, не на холсте: наведение на
  кнопку «документация» блока или связи показывает его отрисованным, клик (или F2) открывает
  окно описания.
- `fromLabel`, `toLabel` — кардинальность или роль на **концах** связи
  (ADR_20260903 §2.6): «1» у одного конца, «0..*» у другого; «owner»,
  «listener». Осмысленны только под ключом `r_*`; у остальных объектов эти
  поля просто не заполняются — каталог не знает и не обязан знать, что стоит
  за ключом, это уже прочитано выше в разделе про `name` у `r_*` (§7.1).
  Каждое — то же провенансное значение (§7.3), что и любое другое поле.

### 7.3 Происхождение

| Поле | Смысл |
|---|---|
| `v` | само значение |
| `at` | **ISO-8601 UTC с `Z`**. Локальные даты и даты без времени запрещены |
| `origin` | `authored` \| `translated` |
| `from` | язык-источник; только у `translated` |
| `fromHash` | хэш **нормализованного** текста источника на момент перевода |

Хэш считается одинаково в `core` и в редакторе (`core.Hash`): текст нормализуется
(CRLF → LF, хвостовые пробелы и табуляции убираются, три и более переносов подряд
схлопываются в два, обрезка по краям), затем FNV-1a 32 бит по **UTF-16 code
units**, результат — 8 шестнадцатеричных цифр в нижнем регистре.

### 7.4 Три состояния и одна проверка

| Состояние | Условие | Действие |
|---|---|---|
| свежий | `fromHash` == хэш текущего значения `from` | ничего |
| протух | `fromHash` != хэш текущего значения `from` | перевести заново |
| разошлись | оба значения `authored`, ни одно не ссылается на другое | конфликт, решает человек; `semaps check` его называет |

**Хэш решает, дата информирует.** Порядок по времени в проверках не участвует:
часы врут, коммиты переставляются, «позже» не значит «новее по смыслу».

**Гранулярность — поле.** Правка `name` не протухляет `doc`.

**Фолбэка нет.** Отсутствие ключа в языке — недостача, а не норма: правило v2
«отсутствующий ключ — фолбэк на базу» отменено. Как рендер поступает с
отсутствующим текстом при показе — его дело; в отчёте это всё равно дыра.

**Правка человеком делает значение `authored`** и снимает `from`/`fromHash`.

### 7.5 Только объекты с происхождением

Значение поля — всегда объект (§7.3). Строка вместо объекта — форма контракта 2: значение
**не читается**, а `semaps check` называет файл, ключ и поле. Приписать авторство тексту,
чьё происхождение никто не записывал, значило бы показать чистую ведомость там, где её нет; а
читать обе формы значило бы навсегда оставить в каждом читателе ветку для файлов, которых, скорее
всего, уже нет ([`ADR_20260927-3`](adr/ADR_20260927-3_core_migrations-outside-the-loader.md)).

## 8. `views/<view_id>.view.json`

```json
{
  "id": "v_semantic_atlas",
  "project": "core",
  "axis": "axis_subsystem",
  "icon": "map",
  "relations": { "default": "visible", "except": ["r_gateway_repguard"] },
  "placements": [
    { "entity": "e_llm", "parent": null,
      "x": -1200, "y": 1400, "width": 1100, "height": 1200 },
    { "entity": "e_llm_middleware", "parent": "e_llm",
      "x": -1120, "y": 1480, "width": 900, "height": 1040,
      "override": { "fill": "#f0fdf4", "border": { "color": "#86efac" }, "header": { "fill": "#dcfce7" } } },
    { "entity": "e_repetitionguardmiddleware", "parent": "e_llm_middleware",
      "x": -950, "y": 1600, "width": 210, "height": 60, "styleId": "class.detail" }
  ]
}
```

### 8.1 `axis` — обязательное поле

Объявляет, **что классифицирует вложенность размещения в контейнер** на этом виде:
`axis_layer`, `axis_subsystem`, `axis_security_zone`, `axis_process`,
`axis_turn`… Множество открытое, имена задаёт проект.

Без оси блок внутри контейнера нечитаем: «живёт в этой сборке», «работает в
этом процессе» и «подвинут, чтобы стрелки не пересекались» выглядят одинаково.

- Вид без `axis` наследует `project.defaultAxis`.
- Нет ни того, ни другого — **схема всё равно открывается**, редактор показывает
  баннер, а вложенность в ней ничего не утверждает и не проверяется. Отказ
  открывать был бы хуже: устаревший файл делал бы проект недоступным.
- Два вида на **разных** осях вправе класть один блок в разные контейнеры. Два
  вида на **одной** оси — нет: это противоречие модели.

Имя файла — `<id>.view.json`; `id` внутри, если есть, главнее имени файла. `id` вида можно
сменить: файл, ключ текста во всех языках и `defaultView` переписываются вместе
([`ADR_20260923-8`](adr/ADR_20260923-8_contract_project-and-view-ids-can-change.md)). Необязательные
`icon`, `theme`, `order` задают строку вида в каталоге (как у проекта, §2). Имени в файле нет —
оно в `text.<lang>.json` под `id` вида (§7.1).

### 8.2 Размещения

Вид — один массив `placements`. Блок и контейнер размещаются одинаково; рамкой размещение
рисуется, если тип его сущности — контейнер (`container: true` в словаре, §6): решает тип
сущности, а не массив в файле.

| Поле размещения | Обяз. | Смысл |
|---|---|---|
| `entity` | да | какую сущность ставим; на виде — не больше одного раза |
| `parent` | да | `entity` размещения-контейнера **на этом виде**, в котором лежит это; `null` — вне контейнеров, это законно |
| `x`,`y`,`width`,`height` | нет | геометрия; нет размера — размер по умолчанию из `canvas.json` (п. 5) |
| `styleId` | нет | стиль этого размещения; нет — стиль типа (§11.5) |
| `override` | нет | частичный стиль одного размещения (§11.6) |
| `template` | нет | шаблон содержимого одного размещения (§11.2) |
| `collapsed` | нет | контейнер свёрнут до шапки |

Правила:

1. **Вид — выборка.** Сущность попадает на холст только вытаскиванием из
   реестра. Контейнера «НЕ РАЗМЕЩЕНО» не существует.
2. **Вложенность записана явно**, из геометрии не выводится. Блок внутри
   рамки, но с `parent: null`, легален. `parent` указывает только на размещение сущности-контейнера
   того же вида; цикл (контейнер в самом себе или в своём содержимом) запрещён.
3. **Вложенность на виде — не принадлежность в реестре.** Принадлежность записывает связь
   `contains` (§4); вид вправе группировать по своей оси иначе. Декоративной рамки без сущности
   нет: «группа для глаз» — сущность типа `group`, и она переносится на другой вид целиком.
4. **Координаты правит человек.** Утилита и скрипт «для восстановления» в `views/`
   не пишут никогда. Агент пишет геометрию только по прямой просьбе человека и только
   в пределах поручения, не затирая чужую раскладку
   ([`ADR_20260924`](adr/ADR_20260924_contract_agent-lays-out-views-on-request.md);
   как устроен вид — инструмент MCP `layout_guide`, [`API.md`](API.md) §6).
5. **Числа геометрии.** `x`,`y` — абсолютные координаты в единицах модели, `y` растёт вниз, начало
   произвольно; у блока внутри контейнера они тоже абсолютные. Блок без размера имеет `node.width` ×
   `node.height` из `canvas.json`, контейнер без размера — `container.minWidth` × `container.minHeight`;
   размер не меньше `node.min*` / `container.min*`, а контейнер не меньше своего содержимого с
   `container.padding` и строкой заголовка `container.headerHeight`. Хост пишет числа как получил,
   без округления до сетки. Новый вид — `{"id","project","axis","placements":[]}`; имя вида — текст
   под его `id` (§7).

Имя и описание контейнера — как у любой сущности: имя нарисованного контейнера — текст `name`
(§7.1), `description` и `doc` — тексты под её `e_`-ключом. Отдельных ключей для рамок нет.

### 8.3 Старая форма

Вид с ключами `zones` или `nodes`, размещение с `zone`, `container` или `id` вместо `entity`, проект
ниже версии 5, `containers.json`, стиль с `kinds` вместо `forKinds` — формы контрактов 3 и 2.
Запись `edges` вида с `from`, `to` или `type` (полная копия связи, §8.5) — прежняя форма контракта 5.
Загрузчик называет файл и поле и не читает такую форму; `semaps check` отвечает тем же текстом;
переписывает её `semaps migrate` ([`ADR_20260927-3`](adr/ADR_20260927-3_core_migrations-outside-the-loader.md),
[`ADOPTING.md`](ADOPTING.md)). Имена `nodes`/`placements`, `entity`/`id`, `zone`/`container` как
равноправные написания больше не принимаются.

§8.4 в контракте нет (раздел удалён, номера дальше сохранены: на §8.5 ссылаются код и ADR).

### 8.5 Видимость связей

Три механизма, по убыванию дешевизны:

1. **Правило обоих концов** — ничего не хранит. Связь видна, только если на виде
   есть **обе** её сущности. Следствие, не настройка; съедает основную массу.
2. **Умолчание** — что делать со связью, по которой решения не принимали:
   `visibility` её типа в словаре (§5, §6), а у типа без неё и у типа вне словаря —
   `relations.default` вида: `visible` для рабочих видов, `hidden` для обзорных.
3. **`relations.except`** — поимённые решения, противоположные умолчанию. Всегда
   меньшая сторона списка.

Умолчание типа лежит на самом типе (в словаре рабочего пространства), а не в политике вида: тип без
`visibility` следует виду, неопределённого состояния нет
([`ADR_20260924-4`](adr/ADR_20260924-4_contract_member-relations-from-code.md) §4). Оно одно на
рабочее пространство: проект, которому нужно иное, решает видом (`relations.default`, `relations.except`).

**Что видимо по умолчанию** из членских связей и новых органических видов:

| Видимо | Скрыто |
|---|---|
| `extends`, `implements`, `contains`, `depends` | — |
| `holds.one`, `holds.optional`, `holds.many`, `holds.many.ro`, `holds.keyed`, `holds.keyed.ro` (открытые члены) | `holds.*.internal` (непубличные члены) |
| — | `uses`, `injects` |

**Ключ `edges` в виде — перекрытие реестра, а не его копия.** Линия — связь реестра
(`relations.json`); у вида своей линии нет, как нет у него своей сущности. Что видно, решают только три
механизма выше: запись в `edges` на видимость не влияет, а вида «с собственным списком линий» нет.
Вид без линий — `relations.default: "hidden"`. Запись `edges` — ссылка на связь и только своё:
`{ "id", "styleId"?, "override"?, "routing"? }`. Концы и тип — из `relations.json`, поэтому `from`, `to`,
`type` в записи не пишутся. Запись без единого из трёх полей не пишется, `id` в списке не повторяется и
обязан быть `id` связи реестра; вид без таких записей ключа `edges` не имеет. Цвет, толщина и штрих
**одной** связи на этом виде — `override` записи (§11.6), а не новый стиль. Линия, существующая только на
виде, невозможна: нарисованная человеком связь — связь реестра `origin: authored`. Показать или скрыть
линию на виде — правка `relations.except` (то же делает `set_relation_visible`); «удалить» связь из кода
на виде — то же скрытие.

**`routing` на ребре вида** — override режима роутинга для одной связи на одном
виде (ADR §2.7); живёт в записи `edges` этой связи. Хранится только выбор (`bezier` \| `orthogonal` \|
`tree-horizontal` \| `tree-vertical`); вычисленная ломаная **не хранится
никогда** — роутер чистая функция от портов и препятствий, пересчитывается на
каждой перерисовке. Каскад — §11.3.

## 9. Инварианты, которые обязан держать любой писатель файлов

1. `id` сущности не меняется никогда; переименование — только имени: у нарисованной сущности это
   правка её текста `name`, у сущности из кода — `name` в `entities.json`.
2. Текст живёт в каталогах текстов. В `relations.json` подписей нет, в
   `entities.json` описаний нет, а имени у нарисованной сущности нет.
3. Имя сущности из кода не переводится; имя нарисованной — переводимый текст.
4. `at` — всегда UTC с `Z`.
5. Правка значения человеком делает его `authored` и снимает `from`/`fromHash`.
6. В `views/` пишет редактор по действию человека и агент по прямой просьбе человека;
   утилиты — никогда (§8.2 п. 4).
7. Сохранённая запись реестра из кода (`origin` не `authored`) не удаляется. Созданную в несохранённом
   состоянии можно отозвать (`ADR_20260930-8`); сохранённую авторскую (`entity` или `relation` с
   `origin: authored`) можно удалить (`ADR_20261001`): тем же пакетом уходят её размещения, `edges`,
   `relations.except` и тексты под её `id`, у сущности — и её связи, висячих ссылок не остаётся. Удаление —
   несохранённое изменение: `Сохранить` пишет файлы без записи, `discard` возвращает её (`API.md` §3.4).

## 11. Оформление блока: `shape`, `template`, роутинг

Три независимые оси блока — контур, стиль и содержимое —
[`ADR_20260903`](adr/ADR_20260903_diagrams_content-templates-and-edge-routing.md)
§2.1. Поля `shape` и `template` объявлены не в этом контракте, а в
`styles.json` — этот раздел
только сводит их вместе с реестрами, которые они адресуют.

### 11.1 `shape` — контур

Поле блочного стиля, значения: `rect` (умолчание) \| `ellipse` \| `diamond` \|
`cylinder` \| `hexagon` \| `actor`. Форма — «что это», поэтому в `override`
размещения (§11.6) её нет: другая форма — другой стиль (пример — `usecase`,
`store`, `decision`, `stage`, `actor` в `styles.json`).

### 11.2 `template` — содержимое

Поле блочного стиля: `id` записи из
`templates.json`.
Формат реестра — массив шаблонов, у каждого `id`, `name`, необязательный
`description` и `lines` (текст шаблона, построчно — так диффы остаются
построчными, компилированное дерево в файл не попадает никогда, ADR §2.3):

```json
{ "id": "class", "name": "Класс / интерфейс",
  "lines": ["@Name", "@Members([name, type], where=kind:field)"] }
```

**Язык шаблона** (ADR §2.3): перенос строки — вертикальный стек, `|` внутри
строки — колонки, `@Directive(позиционный, имя=значение)`. Директивы первой
очереди — `@Name`, `@Description`, `@Members([поля], where=kind:…)`,
`@Asset(имя, h=…, w=…)`. Пустая секция ничего не рисует и не занимает места.

**Каскад назначения**, от частного к общему: размещение → стиль → встроенный
дефолт `title-only` («только заголовок»). Отсутствие значения означает
наследование дальше по цепочке.

### 11.3 `routing` — форма линии связи

Значения: `bezier` (умолчание, текущая кривая) \| `orthogonal` \|
`tree-horizontal` \| `tree-vertical`. Хранится только выбор режима —
вычисленная ломаная не сохраняется нигде (ADR §2.7, и §8.5 выше).

**Каскад выбора**, от частного к общему: `routing` на ребре вида (§8.5) →
`routing` вида целиком → `routing` стиля связи (§11.5: стиль, найденный по
каскаду, — `styleId` записи, базовый стиль типа связи, стиль с `id`, равным типу
связи, например `extends`, `call`) → встроенный дефолт `bezier`. Уровень
«тип связи» делает основную работу: у большинства рёбер `routing` вообще не
задан ни на ребре, ни на виде.

### 11.4 Реестр содержимого (`@Asset`)

`content/index.json` —
манифест картинок для директивы `@Asset(имя, …)`:

```json
{ "assets": [
  { "id": "brain", "name": "Мозг", "file": "content/brain.svg",
    "description": "Обобщённая «думающая» сущность." } ] }
```

Сами файлы (`content/*.svg`) лежат рядом с манифестом и раздаются как обычная
статика. Перед вставкой в DOM SVG **обязательно санируется** — белый список
элементов и атрибутов, без `<script>`, обработчиков событий и внешних ссылок
(`editor/src/assets/sanitizeSvg.ts`); картинки приносят откуда
попало, а рисуются внутри привилегированного окна редактора.

### 11.5 Тип и стиль

`kind` сущности (§3) — **что это**; `styleId` размещения (§8.2) — **как это
выглядит** на этом виде. Одно другое не меняет
([`ADR_20260927-5`](adr/ADR_20260927-5_editor_kind-and-style-apart.md)). Стиль принадлежит
типу ([`ADR_20260927-6`](adr/ADR_20260927-6_contract_v5-kinds-and-containers.md),
[`ADR_20260927-7`](adr/ADR_20260927-7_contract_style-belongs-to-a-type.md)), и стиль связи —
тоже типу, типу связи ([`ADR_20260930-2`](adr/ADR_20260930-2_contract_edge-style-belongs-to-a-relation-type.md)):
**связь устроена так же, как сущность**.

**`appliesTo`** стиля: `block` (умолчание) \| `container` \| `edge`. Размещение сущности-контейнера
берёт стили `container`, остальные размещения — `block`, ребро — `edge`.

**`forKinds`** — типы, за которыми числится стиль: `id` типов сущностей (`["class", "record"]`) у стиля
`block` и `container`, `id` типов связей (`["extends"]`, `["holds.many"]`) у стиля `edge`. Обязателен
у всех, кроме трёх запасных `default.node`, `default.container`, `default.edge`; **не
наследуется** через `basedOn` (вариант внешнего вида — не вариант смысла: «Компонент», нарисованный
как класс, не становится классом). Стиль может числиться за несколькими типами (`class.detail` — за
`class`, `record`, `struct`). Редактор предлагает стиль только его типам; стиль без `forKinds` в
`styles.json` рабочего пространства не теряется — редактор показывает его отдельно («Без типа»), а
`semaps check` перечисляет, пока ему не назначат тип; `forKinds`, названный не по адресу (тип не
из словаря, стиль контейнера за типом не-контейнером), `check` тоже называет. Поле называлось
`kinds`; загрузчик его не читает.

**Каскад стиля размещения**: `styleId` размещения → `style` типа сущности в словаре (§6) → стиль,
чей `id` равен `kind` → `default.node` / `default.container`; поверх найденного — `override`
размещения (§11.6).

**Каскад стиля связи** — тот же: `styleId` записи ребра вида (§8.5) → `style` типа связи в словаре
(§6, `relationGroups`) → стиль, чей `id` равен типу связи → `default.edge`; поверх найденного —
`override` записи ребра (§11.6). Тип связи — `type` связи в `relations.json` и `id` записи
словаря (§5, §6). Цвет, толщина и штрих **одной** связи на одном виде задаются `override` её записи
в `edges` вида — записи-ссылки на связь реестра (§8.5).

Базовый стиль типа явным `styleId` не записывается: `styleId` нужен только для другого варианта
того же типа. Смена типа снимает `styleId`. Цвет одного размещения или одной связи — не стиль, а
`override` (§11.6): цветных стилей контейнеров («Зона · red») нет.

**Значки — ключи реестра иконок.** `icon.glyph` в стиле и в `override` — ключ реестра иконок
редактора (`editor/src/ui/iconSet.ts`; значки типов — `editor/src/ui/kindIcons.ts`), не эмодзи;
неизвестный ключ рисуется запасной иконкой
([`ADR_20260929_editor_icons-are-registry-keys`](adr/ADR_20260929_editor_icons-are-registry-keys.md)).
В словаре `kinds.json` значков нет: тип получает значок через свой стиль.

### 11.6 `override` — частичный стиль одного размещения или одной связи

Выделить один блок, контейнер или связь, не заводя стиль ради них. Форма — та же, что у стиля, но
разрешены только поля из таблицы; остальные отвергает запись (`Apply`, `422`) и называет
`semaps check`. Список расширяется одной строкой в таблице кода (`core/override.go`) и одной в
таблице ниже — больше ничего менять не нужно.

Размещение (`override` в `placements[]`):

| Поле | Смысл |
|---|---|
| `fill` | заливка |
| `border.color` | цвет рамки |
| `border.dash` | штрих рамки (SVG `stroke-dasharray` или `none`) |
| `header.fill` | заливка шапки контейнера |
| `icon.glyph` | значок: ключ реестра иконок |

Запись ребра вида (`override` в `edges[]`, §8.5):

| Поле | Смысл |
|---|---|
| `line.color` | цвет линии |
| `line.width` | толщина линии |
| `line.dash` | штрих линии (SVG `stroke-dasharray` или `none`) |
