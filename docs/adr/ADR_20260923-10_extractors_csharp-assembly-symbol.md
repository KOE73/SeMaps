# ADR_20260923-10_extractors — C#: проект (сборка) — символ `module` с рёбрами `contains`

Статус: **принято**.

## Контекст

Извлекатель C# печатал пространства имён (`module`/`namespace`) и типы, но не проект. Реальные
реестры уже держат сборки руками или скриптом из `ADOPTING.md`
(`{"id":"e_asm_onnx","name":"NeuroModFlowNet.ONNX","kind":"assembly","codeRef":"src/NeuroModFlowNet.ONNX/NeuroModFlowNet.ONNX.csproj"}`),
а классы — с `codeRef` на свои `.cs`, и связи «сборка содержит класс» нет ни в фактах, ни в
реестре. Для C# сборка — единица развёртывания и зависимостей; пространство имён её не
заменяет: одно пространство живёт в нескольких сборках, одна сборка держит несколько
пространств. Сверка ([`ADR_20260923-9`](ADR_20260923-9_core_sync-symbol-mapping-and-containment.md))
уже рассчитывает на символ `{kind: module, nativeKind: assembly}` с рёбрами `contains`.

[`ADR_20260923-5`](ADR_20260923-5_extractors_symbol-ids.md) не даёт формы `id` для сборки, а
очевидная — имя сборки — совпадает с id корневого пространства имён (`Sample.App` —
и сборка, и пространство).

## Решение

1. **Каждый загруженный проект** — символ: `kind: "module"`, `nativeKind: "assembly"`,
   `name` — `AssemblyName`, `namespace: ""`, `file` — путь `.csproj` относительно `root`,
   без `line` и `visibility`. Печатается, если `.csproj` лежит под `root` и проходит
   `--include`/`--exclude`.
2. **`id` — имя сборки в квадратных скобках**: `[Sample.Core]`, как IL пишет ссылку на сборку
   (`[mscorlib]System.Object`). `[` не бывает в метаданном имени пространства имён или типа
   C#, поэтому `id` сборки не сталкивается с id по ADR-5 даже при совпадении имён. `id` не
   зависит от пути `.csproj`: перенос проекта в другой каталог его не меняет, как перенос файла
   не меняет `id` типа.
3. **`contains` сборка → тип верхнего уровня** для каждого типа, объявленного в исходниках
   этого проекта (после исключений §3 `EXTRACTOR.md`). Вложенный тип остаётся под внешним,
   ребра от сборки у него нет. Файл, подключённый в два проекта (`<Compile Include>`/`Link`),
   даёт один символ типа и `contains` от **обеих** сборок: это правда о коде.
4. **`references` сборка → сборка** для каждого `ProjectReference` между проектами этого
   вывода. Ссылки на NuGet и внешние сборки не печатаются (§2.2: только символы вывода).
5. **Мульти-таргетинг** (`TargetFrameworks`): Roslyn открывает проект по разу на TFM; все они —
   один символ по `AssemblyName`, рёбра объединяются. Два разных `.csproj` с одним
   `AssemblyName` — тоже один символ, `file` — первый по ordinal-сортировке путь.

## Отвергнуто

- **`id` = путь `.csproj`** (`src/X/X.csproj`). Совпадает с `codeRef`, но меняется при
  переносе каталога — ключ сверки сломался бы от реорганизации дерева без изменения кода.
- **`id` с текстовым префиксом** (`assembly:X`). Работает так же, но придумано здесь; форма
  IL знакома читателю C# и тоже не пересекается с именами.
- **`nativeKind: "project"`.** Реестры уже говорят `assembly`; сверка переносит `nativeKind` в
  `kind` сущности как есть (ADR-9 п. 6), и другое слово дало бы вторую разновидность того же.
- **`contains` сборка → пространство имён.** Пространство имён не принадлежит одной сборке;
  ребро было бы ложным для каждого пространства, растянутого на две сборки.

## Следствия

- `EXTRACTOR.md` §2.2, §2.3, `extractors/csharp/README.md`, `PLAN_20260923_extractors_csharp`
  описывают символ сборки; `expected.json` переснят, в `testdata/Sample` — общий файл,
  подключённый в оба проекта.
- Сверка усыновляет ручную запись сборки правилом 1 ADR-9 (тот же `codeRef` и `name`), если
  `name` записи равно `AssemblyName`. Проект с `<AssemblyName>`, отличным от имени файла, и
  запись, названная по файлу, автоматически не усыновятся: `symbol` ставит человек.
