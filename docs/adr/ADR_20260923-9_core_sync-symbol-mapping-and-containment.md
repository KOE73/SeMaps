# ADR_20260923-9_core — Сверка: ключ `symbol`, усыновление ручных записей, `contains` в реестре

Статус: **принято**.

## Контекст

`semaps sync` ([`PLAN_20260923_core_sync-with-code`](../plans/PLAN_20260923_core_sync-with-code.md),
шаги 2–3) должен выдавать id сущности один раз и навсегда ([`EXTRACTOR.md`](../EXTRACTOR.md) §5),
а на следующем прогоне узнавать ту же сущность. `id` фактов — ключ сопоставления между
прогонами ([`ADR_20260923-5`](ADR_20260923-5_extractors_symbol-ids.md)), но в контракте реестра
([`CONTRACT.md`](../CONTRACT.md) §3) места для него не было: по `name` искать нельзя (имя правит
человек, классы с одним именем живут в разных пространствах имён), по `e_`-id — тоже (он выведен
из имени один раз и после переименования в коде с ним не совпадает).

Второе: реальные реестры уже существуют. Сборки заведены скриптом из `ADOPTING.md`
(`{"id":"e_asm_onnx","kind":"assembly","origin":"code","codeRef":"…/X.csproj"}`), классы —
руками, иногда без `origin`. Первый прогон, выдающий им новые id рядом со старыми, сломал бы
все виды, где эти id стоят.

Третье: редактор получает панель «Окрестность», которая ходит по связям (сборка → её типы →
наследники). Вложенность нужна ей как связь реестра, а `EXTRACTOR.md` §5 писал в реестр только
`extends`/`implements`. Извлекатель C# начинает печатать `.csproj` символом
`{kind: module, nativeKind: assembly}` с рёбрами `contains` сборка → тип.

## Решение

1. **Поле `symbol` у сущности** — `id` символа из фактов извлекателя. Пишет его только сверка;
   сопоставление на следующих прогонах идёт по нему, а не по имени. Переименование в коде,
   подтверждённое человеком, — это правка `symbol` (и при желании `name`) у старой записи;
   `id` остаётся.
2. **Усыновление при первом прогоне.** Запись без `symbol` и не `authored` сопоставляется с
   символом двумя правилами по порядку:
   1. тот же файл (`codeRef` без якоря `#…`/`:…`) и то же имя; если таких символов
      несколько (модуль-файл TypeScript и его класс), выбирается тот, чей `nativeKind` равен
      `kind` записи, затем — того же семейства;
   2. то же `namespace`, то же имя и то же семейство вида.

   **Имя** сравнивается без хвостового списка параметров типа и без арности: руками пишут
   `IRunner<in TIn, out TOut>`, извлекатель печатает `IRunner` (id ``…IRunner`2``).
   **Семейство вида** — последний сегмент через `-` без учёта регистра: `abstract-class`,
   `static-class`, `sealed-class` ~ `class`, `record-struct` ~ `struct`. Руками пишут `class`,
   извлекатель различает модификаторы. Первый прогон на живом реестре (388 записей, 56 из них —
   generic) без этого давал 33 ложных кандидата на переименование, 83 ложно пропавших и
   дубли `e_converterbase_2`; с ним — все 388 усыновлены.

   Совпадение должно быть однозначным в обе стороны. Иначе ни запись, ни символы не трогаются
   (новые не заводятся), а в отчёте — «неоднозначно»: `symbol` ставит человек. Усыновлённая
   запись получает `symbol` и `origin: code`; её `id`, `name`, `kind` и все чужие поля остаются.
   **`kind` сверка не переписывает никогда** — ни при усыновлении, ни потом: `class` у
   абстрактного класса — выбор человека (стили и фильтры ключуются по `kind`), а точный вид
   доступен в фактах. Новая запись получает `nativeKind` как есть (`abstract-class`), поэтому
   в одном реестре `class` и `abstract-class` соседствуют; это видно и так и задумано.
3. **Кто подлежит сверке.** Запись с `origin: code` или с `symbol` (и не `authored`). Запись без
   `origin`, не нашедшая символа, сверку не касается вовсе — её завёл человек под что-то своё.
4. **Кандидат на переименование удерживается.** Пропавшая запись и новый символ того же файла
   и того же вида не решаются сверкой: запись не помечается `missing`, символ не получает `e_`.
   Отчёт держит их, пока человек не поставит `symbol` или не повторит с `--no-renames`
   (тогда это просто «пропала» + «новая»). Иначе переименование класса порождало бы мусорную
   запись, которую пришлось бы удалять, а удалять записи реестра нельзя.
5. **`contains` пишется в `relations.json`**, как `extends` и `implements`: тип `contains`,
   `origin: code`, и заводится в `relation-types.json`, если его там нет. `references` по-прежнему
   не пишется — только счёт в отчёте «к сведению».
6. **Символ `module` — такая же сущность**, как тип: `kind` сущности = `nativeKind` символа
   (`assembly`, `namespace`, `file`). Общий словарь `kind` фактов в реестр не попадает.
7. **Новый id** — `e_` + slug, где slug — строка в нижнем регистре, в которой всякая серия
   не-букв и не-цифр заменена одним `_`; занято — `_2`, `_3`. Точки и прочее в id не
   пускаются: id — ключ текстов и часть id связей. Что идёт в slug:
   - тип, функция, значение — короткое имя: `RepetitionGuard` → `e_repetitionguard`;
   - **модуль — `nativeKind` и весь `id` символа**: `e_namespace_neuromodflownet_onnx_diagnostics`,
     `e_assembly_neuromodflownet_onnx`, `e_file_editor_src_canvas_diagramcanvas`. Короткие имена
     модулей (`Diagnostics`, `Tracking`, `Algorithms`) повторяются между сборками и читаются
     как чужое (`e_diagnostics` рядом со сборкой `….Diagnostics`), а пространство имён и
     сборка часто называются одинаково — без вида в id они получали бы `_2`.
8. **Состояние ухода — `missing`**, как в `CONTRACT.md` §3; `gone` из прежнего текста
   `EXTRACTOR.md` §5 было опиской.
9. **Проект — один на прогон.** Символы фильтруются по `project.json → sources.include`;
   проектов несколько — нужен `--project`.

## Отвергнуто

- **Ключ по `codeRef` + `name` на каждом прогоне.** Ломается на переносе файла и на
  переименовании; ради этих двух случаев сверка и нужна.
- **Id сущности = id символа** (`e_acme_agent_guards_repetitionguard`). Id длинные, а
  переименование пространства имён превращало бы каждую сущность в новую.
- **Отдельный файл соответствия** (`symbols.json`: символ → `e_`). Ещё один файл, который
  может разойтись с `entities.json`; сущность без своей строки в нём снова стала бы «ничьей».
- **Переписывать `kind` из `nativeKind` при каждом прогоне**, чтобы реестр был единообразен.
  Затирает решение человека и меняет стиль узлов на уже разложенных видах.
- **Словарь совместимых видов по языкам** (`abstract-class` ~ `class` для C#, …) вместо правила
  «последний сегмент». Язык-специфичное знание в `core/`; соглашение `<модификатор>-<вид>` в
  `nativeKind` дешевле и держится извлекателями.
- **Вложенность как вычисляемое свойство** (панель сама читает факты). Факты не лежат в
  workspace, и редактор их не знает; реестр — единственное, что он читает.
- **Заводить новую запись при кандидате на переименование** и оставлять решение человеку.
  Решение тогда означает удаление записи — операцию, которой в контракте нет.

## Следствия

- `CONTRACT.md` §3 получил поле `symbol`, §4 — `contains` среди порождённых типов связей;
  `EXTRACTOR.md` §5 — правила выше; `ADOPTING.md` — `semaps sync`.
- Проект со смешанными языками одним `sources.include` сверяется неверно: факты одного языка
  пометят `missing` записи другого. Пока — один язык на проект; язык при `symbol` не хранится.
- `semaps check` будет требовать имени для `rt_contains` (как для любого объявленного типа):
  это текст, и его пишет человек.
- Объём: сверка заводит сущность на **каждый** символ, включая приватные
  ([`ADR_20260923-6`](ADR_20260923-6_extractors_all-declarations-with-visibility.md)). Если
  реестр живого проекта станет неподъёмным, порог — новым ADR (`EXTRACTOR.md` §6).
