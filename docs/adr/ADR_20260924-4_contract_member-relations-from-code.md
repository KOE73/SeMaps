# ADR_20260924-4_contract — Связи из кода: по членам, признаками, а не именами обёрток

Статус: **принято**. Заменяет [`ADR_20260924-2`](ADR_20260924-2_core_sync-writes-references.md)
целиком: `references` между типами уходит, «скрыт по умолчанию» переезжает на членские связи.
Уточняет [`ADR_20260831`](ADR_20260831_diagrams_text-provenance-and-view-axes.md) §2.13 (у связи из
кода появляется подпись из структуры, не из текстов).

## Контекст

`references` схлопывал все упоминания `A → B` в одно ребро и терял то, ради чего на схему
смотрят: `instructions: List<IOp>` и `Instructions: IReadOnlyList<IOp>` — разные связи, у первой
содержимое можно менять, у второй нет; `Dictionary<K, V>` держит и ключи, и значения; поле —
внутреннее устройство, публичное свойство — интерфейс класса. Одна серая стрелка на пару
классов этого не показывает, а композицию из кода не вывести вовсе: владение — знание человека.

Модель проекта гибкая, не академическая: человек хочет видеть, **через что именно** один класс
держит другой, и включать такие связи по одной. Реестр знает всё, вид показывает нужное.

## Решение

### 1. Одна связь на каждое вхождение класса в тип члена

Извлекатель печатает ребро на каждый член, где встречается другой символ вывода, и на каждое
вхождение внутри типа члена (`Dictionary<IOp, IOp>` — два ребра: ключ и значение).

```json
{ "from": "…VmController", "to": "…VmRunOutcome", "kind": "holds",
  "via": { "member": "activeRuns", "memberKind": "field", "modifiers": ["private", "readonly"],
           "text": "ConcurrentDictionary<long, Task<VmRunOutcome>>",
           "path": ["value", "result"],
           "cardinality": "keyed", "mutability": "mutable", "deferred": true } }
```

Виды рёбер извлекателя: `extends`, `implements`, `contains` — как были; **`depends`** — модуль →
модуль (бывший `references` между модулями; между типами `references` больше нет);
**`holds`** — поле, свойство, событие, индексатор; **`uses`** — параметр, возвращаемое значение;
у `function`/`value` — их собственная сигнатура; у псевдонима типа — правая часть.

### 2. Признаки вместо имён обёрток

`List<IOp>` и `IOp[]` — одно и то же: много, менять можно. `IReadOnlyList<IOp>` и
`IEnumerable<IOp>` — много, менять нельзя. Имя обёртки остаётся только в `via.text`, в
подписи. В `via`:

| Признак | Значения | Смысл |
|---|---|---|
| `cardinality` | `one` \| `optional` \| `many` \| `keyed` | сколько объектов держит член |
| `mutability` | `mutable` \| `readonly` | можно ли менять **содержимое коллекции** через этот член; к `one` не относится (`readonly` у ссылки — модификатор члена, не признак) |
| `deferred` | `true` | объект придёт позже: `Task`, `Lazy`, `Promise`, `Func<T>`, `IObservable` |
| `path` | список слотов | путь от внешнего типа к классу: `item`, `key`, `value`, `result`, `arg`, `element:<n\|имя>`, `error`, `arg:<n>`. Словарь слотов открытый, как `nativeKind` |
| `member`, `memberKind`, `modifiers`, `text` | строки | как написано в коде; `memberKind` — `field`, `property`, `event`, `indexer`, `parameter`, `return`, `constructor`, `self` |

**Каждый признак необязателен. Отсутствует — значит «не известно», а не «mutable».** Java
`List<T>`, Rust `Vec<T>` мутабельность из типа не выводят и честно молчат. Незнакомая
обёртка — слот `arg:n`, признаков нет; эвристик по именам нет.

### 3. Тип связи в реестре собирает сверка, не извлекатель

Тип — только то, что меняет вид линии и умолчание видимости. Сверка составляет его из `kind`
и признаков:

- `holds.one`, `holds.optional`, `holds.many`, `holds.many.ro`, `holds.keyed`, `holds.keyed.ro`
  — через **публичный** член (публичный интерфейс класса);
- то же с суффиксом `.internal` — через непубличный член (внутреннее устройство);
- `injects` — `uses` с `memberKind: constructor`;
- `uses` — остальное.

Признак без значения тип не расширяет: `Vec<T>` даёт `holds.many`. `deferred`, ключ/значение,
`optional` внутри `keyed` живут в `via` и подписи, тип не множат; понадобится цвет — добавится
тип, а не перестроится модель. Экспозиция в типе, а не флагом на связи: она и видимость решает,
и вид (внутреннее — тусклее), и не заводит четвёртый уровень правил видимости.

Стили по умолчанию на все типы из кода — в `host/defaults/styles.json`.

### 4. Видимость по умолчанию

Видимы: `extends`, `implements`, `contains`, `depends`, `holds.*` публичные. Скрыты: `holds.*.internal`,
`uses`, `injects`. Сверка ставит `visibility` типу при его заведении (механизм
[`CONTRACT.md`](../CONTRACT.md) §5/§8.5, введён ADR_20260924-2 — он остаётся).

### 5. Фильтр в извлекателе

База — органика: `extends`, `implements`, `contains`, `depends`. Остальные виды — по явному
списку: `--edges holds,injects` в командной строке, `edges: [holds, injects]` у записи
экстрактора в `.semaps`, чекбоксы на странице «Экстракторы». Факты **объявляют**, что в них
есть: `"edgeKinds": [...]` в заголовке; сверка помечает `missing` только связи тех видов,
которые факты покрывают.

### 6. Ключ связи и переименования

Членская связь опознаётся по `(from, to, via.member, via.path)`; смена обёртки (`List` →
`IReadOnlyList`) — та же связь: `id` остаётся, тип и `via` обновляются. Переименование члена
сверка не решает: как у сущностей, она сообщает кандидата («пропала `r_…_old`, появилась
`r_…_new` с теми же `from`, `to`, `path`»), а агент ставит старой связи `via.member` = новое
имя и повторяет сверку — аналог `symbol`. `id` членской связи:
`r_<from>_<to>_<member>[_<path>]`, коллизия — `_2`.

Поле и свойство, которое его отдаёт, — две связи, без свёртки: экспозиция их и так разводит.
`A → A` по-прежнему не печатается (редактор петли не рисует) — осознанная дыра.

### 7. Подпись связи из кода — из структуры

У связи `origin: code` текста в `text.<lang>.json` нет (ADR_20260831 §2.13) — и не будет.
Редактор рисует подпись из `via`: `activeRuns: ConcurrentDictionary<long, Task<…>> [value]`, а
кратность на конце (`0..*`, `0..1`) — из `cardinality`. Код в структуре, человек в текстах.

### 8. Переход — описательно, не в коде

Сверка **не мигрирует**: старые `references` между типами при первой сверке становятся
`missing`, рядом появляются `holds`/`uses`; старые `references` между модулями — `missing`,
рядом `depends`. Что делать — раздел в [`ADOPTING.md`](../ADOPTING.md): перенести включённость
на видах (`except`, `edges`), удалить `missing`-связи старой модели или оставить, добавить
имена новых типов в тексты. Делает агент или человек, инструмент только сообщает.

### 9. Документация по языкам

Таблица соответствия каждого языка (какие типы дают `many`/`keyed`, что считается `readonly`,
слоты, чего язык не даёт) — нормативный документ `docs/extractors/<lang>.md`, правится вместе с
извлекателем. Для языков без извлекателя — заготовка со статусом.

## Отвергнуто

- **Имя обёртки как тип связи** (`field.List`, `field.IReadOnlyList`). Бесполезная конкретика:
  `List` и массив значат одно и то же, а стилей пришлось бы заводить по обёртке.
- **Академическая классификация** (ассоциация / агрегация / композиция). Владение из кода не
  вывести; композицию по-прежнему ставит человек авторской связью.
- **Свёртка поля и свойства-геттера.** Усложняет правило и извлекатели; экспозиция решает то же.
- **Тип по внешней обёртке у свёрнутой пары** — снято вместе со свёрткой.
- **Видимость как флаг на связи.** Четвёртый уровень правил; экспозиция в типе даёт то же и
  ещё вид.
- **Деление `relations.json`** на органику и членские связи. Причина была в агенте, а его
  закрывают фильтр §5 и MCP ([`ADR_20260924-5`](ADR_20260924-5_host_mcp-server.md)); делить
  потом можно без ломки (`relations.<имя>.json` рядом).
- **Миграция в сверке** (усыновление старых `references`, смена типа на месте). Разовая
  работа, которую агент сделает по описанию; код для одного перехода — лишний.
- **Оставить `references` для модулей.** Слово перегружено; `depends` говорит, что это
  зависимость единиц сборки.

## Последствия

- Объём фактов и `relations.json` растёт помемберно, но фильтр §5 держит его в руках: без
  галочек — только органика.
- Существующие реестры с `references` требуют перехода по §8; до него `check` покажет
  `missing`.
- Извлекатели C# и TS переписывают сбор рёбер; схема фактов меняется (`via`, `edgeKinds`,
  словарь `kind`).
