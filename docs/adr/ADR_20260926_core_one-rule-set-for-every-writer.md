# ADR_20260926_core — Один набор правил для всех писателей: проверка в `Apply`, политика агента в глаголах

Статус: **принято**. Развивает [`ADR_20260924-5`](ADR_20260924-5_host_mcp-server.md) («каждое
правило контракта… должно жить в `core/`, а не в обработчике MCP») и
[`ADR_20260925_host`](ADR_20260925_host_model-owned-by-host.md) (модель держит хост). Заменяет
механизм создания из [`ADR_20260923-8`](ADR_20260923-8_contract_project-and-view-ids-can-change.md)
(`/api/save?create=1`); сама возможность менять `id` проекта и вида остаётся.

## Контекст

Модель одна, и запись в неё одна — `Model.Apply`: журнал, «несохранённое», события. Но правила
контракта оказались в двух местах и не совпадали:

- **глаголы агента** (`SetText`, `AddRelation`, `PlaceEntities`, `AddZone`…) проверяли почти всё:
  пустой текст, существование сущностей и типа связи, префиксы `id`, зону размещения;
- **`applyOne`** проверял часть: допустимые поля текста, текст у связи из кода, форму операции.

Редактор шлёт в `Apply` сырые операции и обходил первую группу. Так ADR-5 формально соблюдён —
правила в `core/`, — но редактор их не видит. Следствия видны уже сейчас: редактор выдаёт новым
блокам `id` вида `node_…`, зонам — `zone_…`, хотя контракт требует `e_` и `z_`
([`CONTRACT.md`](../CONTRACT.md) §3, §8).

Рядом — тот же разрыв в структуре и чтении. Проект и вид редактор создавал сам (собирал JSON и
писал `/api/save?create=1`), агент — через `core`; `id` при создании и при переименовании
проверялись разными правилами. Каталог редактор склеивал у себя из диска и снимков модели, MCP
отдавал голый диск; одно и то же несохранённое имя вида один видел, другой нет.

## Решение

### 1. Правило контракта — в `Apply`, для всех

Всё, что делает объект недопустимым по `CONTRACT.md`, проверяется при приёме пакета, кто бы его ни
прислал: редактор, агент, сверка с кодом. Нарушение — отказ всего пакета (`422` в HTTP, ошибка
инструмента в MCP), ничего не записано.

- **Проверяется пакет целиком, после всех его операций.** Порядок внутри пакета не важен:
  сверка кладёт связь раньше её нового типа, редактор — сущность раньше её размещения.
- **Проверяется только то, что пакет создаёт или меняет.** Новый объект — целиком; изменённый —
  только изменённые поля. Старые данные, которые правилу не отвечают, не мешают править что-то
  другое и не мешают править сам объект, пока не трогают нарушенное поле. Правило не делает
  хуже то, что уже есть, и не пускает новых нарушений.
- **Журнал при старте проверку не проходит**: его пакеты уже были приняты.

### 2. Политика агента — в глаголах, только для агента

То, что ограничивает *агента*, а не допустимость данных, остаётся в глаголах MCP:
геометрия только с `requestedByHuman`; чужое размещение не двигается; `id` выдаёт `core`;
удалить нечего — инструмента нет; не дублировать авторскую связь с теми же концами и типом;
«добавить» не перезаписывает существующее. Человек в редакторе этими ограничениями не связан.

### 3. Одна точка создания и один каталог

- Проект и вид создаёт `core.CreateProject` / `core.CreateView`; хост вызывает их из одного
  сервиса для `POST /api/projects`, `POST /api/model/{project}/views` и инструментов
  `create_project` / `create_view`. Правило `id` одно (`core.ProjectIDPattern`,
  `core.ViewIDPattern`) — и для создания, и для переименования. `/api/save` в `projects/` больше
  не пишет.
- Каталог один — `core.LiveIndex`: состав с диска, названия и вид из рабочей модели.
  Его отдают и `/api/workspace`, и `list_projects`.

## Отвергнуто

- **Проверять каждую операцию отдельно, по порядку.** Ломает сверку (связь раньше типа) и
  заставляет каждого писателя помнить порядок.
- **Проверять весь объект при любом изменении.** Один старый `zone_…` запретил бы двигать эту
  зону. Миграция данных — отдельное решение, не побочный эффект проверки.
- **Оставить редактору доверие «человек знает, что делает».** Человек — да; код редактора — нет:
  `node_…` вместо `e_…` — ошибка программы, а не выбор человека.
- **Правила в TypeScript на клиенте.** Второй набор правил — расходятся (тот же довод, что
  в ADR-5 против отдельного MCP-сервера). Проверка в диалоге редактора — только подсказка при
  вводе, решает хост.

## Не решено здесь

- **Кто владеет полями записей `origin: code`.** Редактор сейчас может сменить `name` и `kind`
  блока из кода; сверка вернёт их при следующем прогоне. Запрет ломает правку в редакторе, а
  исключение для `confirm_rename` требует понятия «владелец поля». Отдельное решение.
- **Миграция старых `id` без префикса** (`node_…`, `zone_…` в существующих проектах).

## Последствия

- `applyOne` / проверка пакета вбирают правила из глаголов; глаголы строят операции и держат
  только политику агента. Сообщения об ошибках — те же, что давали глаголы.
- Редактор выдаёт новым объектам `e_…` и `z_…`.
- `docs/API.md` §3.4: пакет проверяется по контракту; §3.4a — создание.
