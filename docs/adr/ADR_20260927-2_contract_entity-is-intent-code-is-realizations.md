# ADR_20260927-2_contract — Сущность — замысел; код — её реализации, от нуля до N

Статус: **принято**. Заменяет в [`ADR_20260923-9`](ADR_20260923-9_core_sync-symbol-mapping-and-containment.md)
ключ сверки (`symbol` у сущности) и правило «усыновлённая запись получает `origin: code`».

## Контекст

У сущности сейчас одна привязка к коду: `codeRef`, `symbol`, `namespace` на верхнем уровне.
Этого не хватает в трёх случаях, и все три — обычная работа SeMaps:

1. **Нарисовал → агент реализовал.** Сущность живёт без кода, потом получает его. Контракт это
   допускал (`codeRef` необязателен), но нарисованная (`authored`) сущность по правилам
   сверки не могла получить `symbol` никогда: сверка находила символ и заводила **вторую**
   сущность рядом с нарисованной.
2. **Одна схема — несколько реализаций.** SDK на нескольких языках, кроссплатформенный агент
   (Windows — C#, Linux — Go), прототип и production, миграция C# → Go. Архитектурная роль
   одна; привязка «сущность = символ» даёт «`StorageCSharp` пропал, `StorageGo` появился»,
   хотя в архитектуре не произошло ничего.
3. **Разные сущности на разных языках** (`Collector` — Go, `Storage` — C#). Работает и
   сейчас, но только потому, что каждая привязана к одному символу.

Связь уже устроена как нужно наполовину: `evidence` — массив. Но `via` (имя члена, обёртка)
лежит на связи, хотя у Go-реализации член `body`, а у C# — `Body`.

И `origin` сейчас значит не то, что написано: сверка переписывает его на `code`, усыновляя
запись, то есть `origin` отвечает «кто за сущность отвечает», а не «откуда она».

## Решение

### 1. `code[]` у сущности

`codeRef`, `symbol`, `namespace` верхнего уровня упраздняются. Вместо них — массив
реализаций:

```json
{ "id": "e_storage", "name": "Storage", "kind": "class", "origin": "authored", "status": "present",
  "code": [
    { "lang": "go",     "ref": "go/storage/storage.go", "symbol": "example.com/demo/storage.Storage" },
    { "lang": "csharp", "ref": "cs/Storage.cs",         "symbol": "Demo.Storage", "status": "missing" }
  ] }
```

| Поле | Обяз. | Смысл |
|---|---|---|
| `ref` | да | путь от корня исходников (как `codeRef` был), для просмотра кода и `check` |
| `lang` | с `symbol` | язык — `language` фактов извлекателя |
| `symbol` | с `lang` | `id` символа в фактах |
| `status` | нет | `missing`, если символ пропал из фактов; `present` не пишется |

- Нет кода — нет `code` (не пустой массив).
- Запись только с `ref` (без `lang`/`symbol`) — ручная ссылка на файл: `.csproj`, схема БД,
  документ. Сверка может её привязать (п. 3).
- **Ключ сверки — пара `(lang, symbol)`**, уникальная в проекте среди всех записей `code[]`.
- `namespace` не хранится: он выводится из `symbol` и у каждого языка свой.
- `members` остаются у сущности; их пишет сверка по **первой** записи `code[]` с `symbol`.
  Члены по языкам — если на живом примере это окажется нужно, отдельным решением.

### 2. `origin` — происхождение, неизменное

`origin` пишется при заведении и **не меняется никогда**: `authored` — нарисовал человек или
агент, `code` — завела сверка. Нарисованная и потом реализованная сущность навсегда
`authored` с непустым `code`: история читается прямо с карты.

То, за что раньше отвечал `origin` («подлежит ли сверке»), выводится из данных: сущность
сверяется **языком L**, если у неё есть запись `code[]` с `lang: L`.

### 3. Сверка по языкам

Прогон извлекателя языка L меняет **только записи `code[]` с `lang: L`** и связи/основания
этого языка. Остальные языки для него не существуют.

| Событие | Реакция |
|---|---|
| символ в фактах, есть запись `(L, symbol)` | обновить `ref`, `members` (если запись первая); снять `status` |
| символ в фактах, записи нет | привязка (ниже); не привязался — новая сущность `origin: code` с одной записью |
| запись `(L, symbol)` есть, символа нет | записи `status: missing` |
| переименование | как раньше, кандидат в отчёт по записям языка L |

**Статус сущности** выводится: `missing`, если у неё есть записи `code[]` с `symbol` и все они
`missing`; иначе `present`. У сущности без кода статус ставит человек (`planned` и т.п.).
Миграция C# → Go: C#-запись `missing`, Go-запись есть — сущность `present`; мёртвую запись
убирают руками или агент.

**Привязка** символа к сущности без записи языка L (прежнее «усыновление», теперь и для
`authored`):
1. запись `code[]` только с `ref`, тот же файл и то же имя — как правило 1 ADR-9;
2. то же имя (без обобщений и арности), совпадение однозначно в обе стороны среди сущностей
   без записи языка L и непривязанных символов; при нескольких символах одного имени — сужение
   по семейству вида. Есть ли у сущности реализации на других языках, не важно: это путь и
   «нарисовал → агент реализовал», и «вторая реализация той же схемы». Семейство вида не
   обязано совпадать: нарисованный `class` реализуется Go-`struct`;
3. иначе — `неоднозначно` в отчёт; привязку ставит агент или человек, дописав запись в `code[]`.

Правило «однофамильцы — одна сущность» держится на именах: у разных ролей разные имена
(`MainServer`/`TestServer`). Где это не так, агент правит запись `code[]` руками.

Одна сущность или две: **взаимозаменяемые** реализации одной роли — одна сущность с N
записями; реализации, одновременно работающие разными узлами системы (основной сервер и
встроенный), — разные сущности, даже если следуют одной спецификации.

### 4. Основания связи по языкам

`via` переезжает со связи в запись `evidence[]`; запись получает `lang`, `symbol`, `native`
(ADR_20260927) и `status`:

```json
{ "id": "r_snake_segment_holds",
  "from": "e_snake", "to": "e_segment", "type": "holds.many", "origin": "authored",
  "evidence": [
    { "lang": "go", "ref": "go/snake.go", "symbol": "demo/game.Snake",
      "native": "field", "via": { "member": "body", "memberKind": "field", "text": "[]Segment", "cardinality": "many" } },
    { "lang": "csharp", "ref": "cs/Snake.cs", "symbol": "Demo.Snake",
      "native": "property", "via": { "member": "Body", "memberKind": "property", "text": "List<Segment>", "cardinality": "many", "mutability": "mutable" } },
    { "lang": "ts", "ref": "ts/snake.ts", "symbol": "snake.Snake", "status": "missing" }
  ] }
```

- `type` связи — замысел: ставится при заведении и сверкой не переписывается. Язык, чей
  выведенный тип другой (`holds.many.ro` против `holds.many`), получает своё основание и
  строку `расходится` в отчёте.
- Ключ членской связи языка L — `(from, to, семейство, evidence[L].via.member, via.path)`.
  Связь без основания языка L, но с тем же `(from, to, семейство)` и единственная такая —
  получает основание L (так нарисованная связь встречает код).
- Статус связи выводится из оснований так же, как статус сущности.

### 5. UI

У блока кнопка «код» — **по одной на запись `code[]`**, на кнопке — метка языка (`go`, `c#`,
`ts`; у ручной записи — расширение файла). Нет кода — кнопок нет. Выбора «языка по
умолчанию» нет: всё видно сразу.

## Отвергнуто

- **Одна привязка и «язык по умолчанию» в проекте.** Прячет реализации; миграция снова
  выглядит как «пропало/появилось».
- **Отдельный реестр реализаций** (`realizations.json`). Разрывает сущность и её код по двум
  файлам ради того, что помещается в одну строку на реализацию.
- **Сущность на каждую реализацию и связь «реализует» между ними.** Утраивает карту ради
  того, что архитектурно одно.
- **`origin` как «кто отвечает».** Смешивает историю и управление; первое теряется при
  первом прогоне сверки.
- **`members` по языкам сразу.** Нет случая, где это нужно; дорого для показа.
- **Запрет автопривязки, если у сущности уже есть реализация на другом языке.** Каждый
  второй язык одной схемы упирался бы в ручную привязку каждой сущности — ровно в том
  сценарии, ради которого `code[]` заведён.
- **Прежнее правило 2 ADR-9 (то же `namespace`, имя и семейство).** `namespace` больше не
  хранится; правило 2 выше его покрывает.
