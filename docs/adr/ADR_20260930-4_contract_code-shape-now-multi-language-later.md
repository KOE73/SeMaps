# ADR_20260930-4_contract — Форма реализаций в коде — сейчас, сверка по языкам — потом

Статус: **принято**. Берёт **форму данных** [`ADR_20260927-2`](ADR_20260927-2_contract_entity-is-intent-code-is-realizations.md)
(`code[]` у сущности, `evidence[]` у связи) и отказывается от её сверки по языкам до тех пор, пока проекту
она не понадобится. Уточняет [`ADR_20260927-4`](ADR_20260927-4_contract_external-symbols.md) (внешний символ —
реализация без `ref`) и [`ADR_20260930-3`](ADR_20260930-3_contract_fact-kinds-and-derived-relation-types.md) §4
(`native` в реестр не пишется). `contractVersion` остаётся `5`.

## Контекст

`ADR_20260927-2` лежал в ветке `contract-v4-realizations`, забытой на другом компьютере: сущность — замысел, её код —
от нуля до N реализаций, по одной на язык. Ветка ушла в сторону от `live-graph` (там v5, контейнеры-сущности,
типы со стилями), и переносить её целиком — значит переносить сверку, которую пока никто не просит.

А форма данных нужна именно сейчас. Рабочее пространство NMFN ещё в контракте 3 и будет мигрировано **один
раз**, вместе с репозиторием самого SeMaps (`examples/`, `docs/diagrams/`); реализации в коде до сих пор лежали
как `codeRef` + `symbol` на сущности и `codeRef` + `symbol` + `via` на связи, и без языка. Возьмём форму позже —
данные придётся мигрировать второй раз, теперь уже у пользователя.

Вторая реализация той же сущности, разные члены `via` у Go и C#, привязка нарисованной сущности к символу — всё это
работа сверки. Она нужна, когда проект действительно держит один замысел на нескольких языках. Такого проекта
сейчас нет.

## Решение

1. **Форма — как в `ADR_20260927-2`.** У сущности необязательный `code: [{lang, ref, symbol, status}]`, у связи
   необязательный `evidence: [{lang, ref, symbol, via, status}]`; `via` живёт только в записи `evidence[]`
   (первая запись, у которой он есть, — подпись члена связи). Нет кода — нет ключа, не `[]`. `lang` и `symbol`
   идут вместе; запись без них — ручная ссылка на файл (`ref`); в записи `evidence[]` допустим один `via`.
   Один язык — не больше одной записи. `status` — `missing` или ничего.
   Упраздняются `codeRef` и `symbol` верхнего уровня у сущности, `via` верхнего уровня у связи,
   `evidence[].codeRef` и `evidence[].line` (номер строки — якорь `:N` в `ref`).
2. **Отличия от `ADR_20260927-2`, все — в сторону «меньше».**
   - `namespace` остаётся полем сущности. `ADR_20260927-2` выводит его из `symbol`, а это знание языка; в `core/` его нет,
     а сверка сравнивает по нему (правило привязки «то же пространство имён, имя и вид»).
   - `native` в реестр **не пишется** (`ADR_20260930-3` §4: он для показа и фильтров, а не для реестра). Добавить
     необязательное поле позже — не миграция.
   - `origin` по-прежнему переписывается сверкой при усыновлении. Неизменный `origin` (`ADR_20260927-2` §2) —
     часть сверки по языкам.
   - `ref` не обязателен у записи с `symbol`: реализация внешнего символа (`io.Writer`) — запись `{lang, symbol}` без
     файла (`ADR_20260927-4`); кнопки кода у неё нет.
3. **Что сделано.** Загрузчик, `semaps check` и правила записи (`core/rules.go`) знают форму и называют старую;
   `semaps migrate` приводит к ней и контракт 3, и уже-v5 прежней формы. `sync` пишет **одну** реализацию —
   запись языка прогона (`language` фактов) — и в остальном ведёт себя, как раньше: ключ — символ этой записи,
   переименования, усыновление, `missing`. Прогон языка L видит только записи языка L: сущность, реализованная
   лишь на другом языке, не помечается `missing`, не усыновляется по имени и не трогается. Граф соединяет символ
   с сущностью по паре `(язык, symbol)`. Редактор рисует по кнопке на реализацию с меткой языка и показывает
   основания связи в инспекторе. MCP `get_entity` ищет по `symbol` любой записи, `confirm_rename` правит
   единственную запись с символом.
4. **Что не сделано и ждёт проекта, которому это нужно.** Привязка символа второго языка к уже существующей
   сущности (по имени или по файлу); статус сущности и связи, выведенный из записей; поле `status` записи никто
   не ставит; строка «расходится», когда выведенный тип связи одного языка иной; неизменный `origin`;
   инструменты `bind_code` и `unbind_code`; `members` по языкам. Реализации, которые пишет автор руками, `check`
   проверяет по форме, а `sync` их не сопоставляет.
5. **Методы и вызовы в `code[]` и `evidence[]` не попадают** — они данные живого графа
   ([`ADR_20260928-3`](ADR_20260928-3_host_calls-live-in-the-graph.md)).
6. **Язык при миграции не угадывается.** `codeRef` + `symbol` становятся записью с `lang`, и язык берётся из
   записи `extractors` файла `.semaps`, когда все извлекатели этого проекта одного языка (один извлекатель или
   несколько одного языка). Иначе `semaps migrate` останавливается и говорит, какие записи ждут языка; ничего не
   записано. Запись без `symbol` (ссылка на файл) языка не требует.

## Отвергнуто

- **Мигрировать данные дважды: сейчас старой формой, потом новой.** NMFN — реальные данные в чужом репозитории;
  вторая миграция — риск без выгоды.
- **Взять сверку по языкам целиком (`ADR_20260927-2` §2–§4).** Её никто пока не просит, а привязка по имени —
  как раз то место, где сверка «угадывает»; правило `ADR_20260928-5` («только однозначные факты») велит подождать
  проекта, которому это нужно, и посмотреть на его случай.
- **Язык проекта одним значением в `project.json`.** Тот же проект не всегда один язык; язык — свойство
  реализации, а не проекта.
- **`lang` необязателен, угадывается по расширению `ref`.** Расширение говорит о файле, а не о языке символа в фактах
  (`.csproj`, `.ts` под ключом `typescript`, ссылки на схемы).
- **Оставить `via` на связи, а `evidence` расширить только языком.** Тогда Go-член `body` и C#-член `Body` одной связи
  снова не поместятся, и форма поменяется второй раз.
