# PLAN_20260925-2_host — Инструменты агента для видов: прочитать, сослаться, разложить

Статус: **выполнен** — шаги 1–6 выполнены; проверка на NeuroModFlowNet.ONNX ниже.
[`PLAN_20260925_host_model-owned-by-host`](PLAN_20260925_host_model-owned-by-host.md): инструменты
меняют рабочее состояние модели, а не файлы, и идут через `/mcp` запущенного хоста.

Решения, на которых стоит план:
[`ADR_20260924`](../adr/ADR_20260924_contract_agent-lays-out-views-on-request.md) — геометрию
агент пишет только по прямой просьбе человека, в пределах поручения, чужую раскладку не трогает;
[`ADR_20260925`](../adr/ADR_20260925_host_model-owned-by-host.md) — результат виден в редакторе
сразу, сохраняет человек. Как устроен вид — [`LAYOUT.md`](../LAYOUT.md).

## Зачем

Задача с живого проекта: в зоне «ONNX tensor transforms» базовый класс и семь однотипных зон
(Undistort, Цвет и нормализация, Perspective, Crop, Resize, PadResize, Rotate90), в каждой — база
семейства слева и наследники справа. Человек разложил одну и десять минут повторял для остальных.
Должно быть: «возьми `v_ops#z_undistort` и сделай остальные в `z_onnx_tensor_transforms` так же» —
одна команда, результат сразу на экране, человек смотрит и сохраняет.

Для этого агенту нужно: **видеть** вид с геометрией, **однозначно понимать**, о каком объекте речь,
**менять** геометрию крупными осмысленными шагами, а не координатами по одной.

## Шаги

Каждый шаг — отдельный коммит, тесты зелёные. Правила записи — в `core` (над `*Model`), инструменты
MCP в `host/mcp.go` — тонкие обёртки. Каждый пишущий инструмент: только с `requestedByHuman: true`
(как `place_entities`), автор `agent`, в ответе — «не сохранено» и ссылка с подсветкой тронутых
объектов (шаг 4 плана модели). Всё, что меняет вид, — одна пачка операций: применяется целиком или
никак.

### 1. Ссылка на объект вида

- **Формат** (в `docs/API.md` и `LAYOUT.md`): `<view>#<id>` — `v_ops#z_undistort`,
  `v_ops#e_op_onnx_crop_nchw_base` (узел — по сущности), в проекте с несколькими моделями
  `<project>/<view>#<id>`. Та же строка — в ссылке редактора: `/app/#v_ops?highlight=z_undistort`.
- **Редактор**: «Копировать ссылку» в контекстном меню блока и зоны (`CanvasMenus.ts`) и кнопка в
  панели «Свойства»; при выделении нескольких — ссылки через запятую. Копирует в буфер строку
  `v_ops#z_undistort` (и показывает тост).
- `core.ParseRef(ref) (project, view, id)`; инструменты принимают ссылку везде, где принимают
  объект вида.
- Тесты: разбор ссылок; неизвестный объект — ошибка с текстом.

### 2. `get_view` — прочитать вид

Только чтение (`readOnlyHint`). Ответ — объект:

- `view`: `id`, `axis`, политика связей;
- `zones`: `id`, `container`, `parent`, `x`, `y`, `width`, `height`, `styleId`, `collapsed`,
  имя (из текстов на языке запроса), вложенные `zones` и `nodes` — **деревом**, как видит человек;
- `nodes`: `entity`, имя и `kind` сущности, `zone`, прямоугольник, `styleId`, `template`;
- `edges`: связи, видимые на виде (правило обоих концов + умолчание типа + `except`, CONTRACT
  §8.5): `id`, `from`, `to`, `type`;
- `unsaved`: есть ли несохранённое у вида и чьё.

Параметры: `view` или ссылка на зону (`v_ops#z_onnx_tensor_transforms`) — тогда только это
поддерево; `lang`. Тест: дерево совпадает с файлом вида; видимость связей — по трём правилам.

### 3. Мелкие операции геометрии

В `core/viewedit.go`, над `*Model`, общими помощниками прямоугольников (порт того, что редактор
делает в `editor/src/geometry/rect.ts`: объединение, отступы, шапка зоны 28, внутренний отступ 16,
сетка 10, минимумы узла 100 × 40 и зоны 160 × 100 — числа из `LAYOUT.md`, одна таблица на оба
языка):

| Инструмент | Что делает |
|---|---|
| `move_elements` | сдвиг `{dx, dy}` или в точку `{x, y}` для узлов и зон; зона едет с содержимым |
| `resize_elements` | новые `width`/`height`; не меньше минимума; зона не меньше своего содержимого |
| `set_zone` | положить узлы/зоны в зону (`zone`/`parent`), координаты не трогает |
| `add_zone` | новая зона: родитель, прямоугольник, `container` или `null`, `styleId`, имя (текст) |
| `fit_zone` | подогнать зону под содержимое: шапка + отступы; по цепочке — родителей, если перестали вмещать |
| `align_elements` | те же режимы, что кнопки выравнивания редактора (левый/правый/верх/низ, ширина/высота по первому) |

Всё округляется к сетке 10. Тесты на каждый: координаты после операции, минимумы, зона едет с
содержимым, `fit_zone` растит родителя.

### 4. `arrange_like` — «сделай остальные так же»

Главный инструмент плана. Параметры: `reference` — ссылка на эталонную зону; `targets` — ссылки на
зоны, которые переложить (или `parent` — все зоны-соседки эталона внутри родителя);
`requestedByHuman`.

Что переносится с эталона на каждую цель:

1. **Роли узлов.** Узлы эталона сопоставляются с узлами цели по месту в иерархии наследования
   внутри зоны: «база семейства» (узел, к которому идут `extends` от других узлов зоны, сам
   наследует снаружи) ↔ база цели; наследники — по порядку имени (или по суффиксу, общему с
   эталоном: `_FP16_NCHW` ↔ `_FP16_NCHW`, `_U8_NHWC` ↔ `_U8_NHWC`). Не сопоставилось — узел
   кладётся в свободный ряд снизу и попадает в отчёт «не нашёл пару».
2. **Раскладка.** Положение каждого узла относительно левого верхнего угла зоны, размеры узлов,
   `template`, `styleId`.
3. **Зона.** Размер (или `fit_zone`, если узлов больше), `styleId`, свёрнутость.
4. **Порядок и шаг** между целевыми зонами внутри родителя — как между эталоном и его соседом, если
   просили `parent`; иначе зоны остаются на своих местах.
5. **Родитель** растёт (`fit_zone`), если перестал вмещать.

Ответ: что сделано по каждой цели, пары узлов «эталон → цель», узлы без пары, «не сохранено» и
ссылка с подсветкой всех тронутых зон. Всё — одна пачка: одна ошибка — ничего не применено.

`dryRun: true` — только ответ, без записи: агент показывает человеку, что собирается сделать.

Тесты — на копии живого случая (зона-родитель, эталон с базой и 3 наследниками, 6 целей с тем же
устройством и одна с лишним узлом): координаты целей повторяют эталон со сдвигом; суффиксы
сопоставлены; лишний узел в отчёте; родитель вырос; `dryRun` ничего не пишет.

### 6. Проверка на NeuroModFlowNet.ONNX

Резервная копия `docs/diagrams` в scratchpad. Сохраниться. Агентом (Claude Code, `.mcp.json`):

1. `get_view` на `v_ops#z_onnx_tensor_transforms` — дерево с семью зонами.
2. Сбить руками раскладку в двух зонах, сохранить.
3. «Сделай остальные зоны в … как `v_ops#z_undistort`» — сначала `dryRun`, потом выполнить.
4. В открытом редакторе зоны переложились без F5; значок «не сохранено» у вида.
5. «Отменить несохранённое» у вида — всё вернулось; повторить и сохранить.

Результат (время, что не сопоставилось, что пришлось поправить руками) — в этот план.

### Результат проверки (шаг 6, 2026-09-25)

Хост — сборка этого коммита, проект NeuroModFlowNet.ONNX, порт 32905. «Агентом» был скрипт по
`/mcp` с ключом хоста (те же вызовы, что у Claude Code); реального Claude Code с `.mcp.json` не
запускали. Файлы `docs/diagrams` после проверки возвращены из резервной копии, расхождений 0.

- **Зона.** `z_onnx_tensor_transforms` в этом проекте нет (это пример из другого). Взяли живой
  аналог: родитель `z_transform` с семью зонами `z_tr_*`, эталон `z_tr_undistort`.
- **Формат файла.** У зон `container` называет зону-родителя, а `parent` пуст; вложенность зон
  нигде не записана, кроме прямоугольников. Поэтому зона вкладывается по `parent`, иначе по зоне в
  `container`, иначе по наименьшей зоне, чей прямоугольник её вмещает.
- **1.** `get_view v_ops#z_transform`: семь зон с 3–4 узлами, 29 линий, 33 мс, 10 КБ.
- **2.** Руками (операции человека) сбиты узлы в `z_tr_crop` и `z_tr_resize` (8 узлов), сохранено.
- **3.** `arrange_like` с `reference: v_ops#z_tr_undistort`, `parent: v_ops#z_transform`:
  `dryRun` (99 мс) — 6 зон, 27 объектов, ничего не записано; затем выполнение (87 мс). Пары нашлись
  во всех зонах; в `z_tr_color` нет варианта u8 — попал в «нечего сопоставить», лишних узлов нет.
  Зоны сложены столбиком с шагом 30 (шаг эталона), узлы легли по образцу, родитель вырос (2110 → 2200).
  Повторный запуск: 0 объектов.
- **4.** SSE отдал событие `agent:27`; в открытом редакторе (проверено в браузере на `move_elements`)
  зона переехала без F5; файл до Save не менялся, реестр не тронут.
- **5.** «Отменить несохранённое» у вида вернуло сбитую раскладку точно; повторный запуск и Save
  записали файл.
- **Что пришлось поправить по ходу.** Первая версия сопоставляла по словам из id: id в нижнем
  регистре, и в `z_tr_color` (`…rgbfp16nchw…`) пары не нашлись. Теперь слова берутся из имён
  сущностей (`BgrU8Hwc_To_RgbFP16Nchw`), с разбиением по горбам и цифрам. Тест на этом случае есть.
- **Руками не правилось ничего.** Не проверено: значок «не сохранено» у вида в каталоге на глаз.
